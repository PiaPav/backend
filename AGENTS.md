# Общие инструкции проекта

Ты работаешь с этим репозиторием автономно.

## Общие правила

- Перед внесением изменений изучай существующую архитектуру и реализацию.

- Не перерабатывай работающие компоненты без конкретной необходимости.

- Сохраняй обратную совместимость, если задача явно не требует её нарушения.

- Следуй существующему стилю кода и соглашениям проекта.

- Не изменяй файлы за пределами текущего репозитория.

- Не читай и не изменяй секреты, если это не требуется задачей.

## Политика Git

- Git-контроль централизован у `orchestrator`: он проверяет состояние рабочей директории перед изменениями, готовит
  единый diff после реализации для ревью и перед коммитом убеждается в актуальности diff. Не повторяй одинаковую
  Git-проверку без изменений или конкретной причины.

- Для анализа разрешены операции чтения, предусмотренные политикой OpenCode: `git status`, `git diff`, `git log`,
  `git show`.

- `coder` и `tester` не выполняют рутинные Git-проверки: сведения о состоянии и diff по необходимости предоставляет
  `orchestrator`. Все Git-операции записи для них запрещены. `architect`, `reviewer` и `math_reviever` не запускают Git
  или какие-либо команды и работают только с доступными средствами чтения. Результаты своей работы агенты передают
  `orchestrator`.

- Агент `orchestrator` после успешного тестирования и финального ревью обязан проверить итоговый diff, добавить в индекс
  только относящиеся к текущей задаче файлы с помощью `git add` и создать локальный коммит с помощью `git commit`.

- Перед `git add` и `git commit` агент `orchestrator` обязан убедиться, что в коммит не попадут посторонние
  пользовательские изменения, сгенерированные файлы, секреты или иные файлы вне области задачи.

- Если роль допускает использование Git, каждую Git-команду выполняй отдельным вызовом Bash. `architect`, `reviewer` и
  `math_reviever` никогда не используют Bash.

- Не выполняй без явного требования пользователя другие операции, изменяющие состояние Git: `reset`, `checkout`,
  `switch`, `branch`, `merge`, `rebase`, `cherry-pick`, `stash`, `tag`, `update-ref` и аналогичные.

- Push и любые другие операции записи в удалённый репозиторий запрещены для всех агентов, в том числе для
  `orchestrator`. Запрещены force push, удаление веток и переписывание истории.

- Не выполняй несвязанный с задачей рефакторинг.

## Порядок разработки

Для каждой существенной задачи:

1. Проанализируй репозиторий и текущую реализацию.

2. Определи затрагиваемые компоненты.

3. Сформируй план реализации.

4. При необходимости используй специализированных субагентов.

5. Реализуй изменение.

6. `coder` добавляет или обновляет необходимые unit- и регрессионные тесты вместе с реализацией, без запуска тестовых
   команд.

7. `tester` независимо оценивает покрытие требований, при необходимости создаёт или обновляет дополнительные тестовые
   файлы (не меняя продуктовый код), выполняет релевантные тесты и отправляет результаты `orchestrator`. Отсутствие
   реально выполненных проверок не считается успешным тестированием даже при коде возврата 0. Не требуется создавать
   новые тесты для каждой тривиальной правки.

8. `orchestrator` получает единый diff; `reviewer` оценивает его статически вместе с отчётом `tester`, без консоли и
   повторных запусков.

9. Существенные дефекты исправляет `coder` по поручению `orchestrator`.

10. `tester` повторяет необходимые проверки только при фактическом изменении кода/тестов или документированной причине.
    Повторное ревью — только при содержательных новых изменениях или неустранённых замечаниях.

11. После успешных тестов и ревью `orchestrator` удостоверяется в актуальности diff, добавляет в индекс только файлы
    текущей задачи и создаёт локальный коммит.

Задача не считается завершённой, пока реализация и проверка не закончены.

Не останавливайся на этапе предложения решения или написания плана, если пользователь запросил реализацию.

## Разделение ролей и выбор Python

- `architect`, `reviewer` и `math_reviever` никогда не запускают команды, консоль, скрипты, тесты, линтеры, Git CLI или
  другие программы, в том числе через косвенные инструменты и делегирование. Они выполняют только статический анализ.
  Общие требования запускать тесты или проверять Git на них не распространяются.
- `orchestrator` сначала определяет тип запроса. Для теоретического ответа, консультации, чтения файлов и статического
  анализа без изменений и исполнения Python не нужен и не запрашивается. Для реализации, изменения файлов проекта или
  исполнения кода до исполнительных действий обязан получить **от пользователя** полный путь к `python.exe` либо
  директории виртуального окружения; если его нет — спросить и дождаться ответа, не подбирать путь самостоятельно.
  Исключение: создание и редактирование обычной документации штатными инструментами OpenCode не требует Python и
  выполняется `orchestrator` самостоятельно, без обязательного делегирования coder.
- `orchestrator` обязательно передаёт предоставленный пользователем путь `coder` и `tester` **в каждом задании**,
  включая повторные вызовы. `coder` и `tester` запускают Python и Python-инструменты только через соответствующий
  интерпретатор внутри этого пути; при отсутствии или ошибке пути блокируют запуск и запрашивают уточнение через
  оркестратор.
- `coder` отвечает за реализацию и unit-/регрессионные тесты, `tester` — за независимые дополнительные тесты, их
  исполнение и диагностику, `reviewer` — за статическое ревью, `orchestrator` — за Git-контроль, делегирование и коммит.
  Никто не повторяет проверку другого агента без обоснованной необходимости.
- Явные пожелания пользователя о распределении написания тестов учитываются, если не противоречат обязательным
  ограничениям ролей и безопасности.
- Эти специальные правила имеют приоритет над общими указаниями автономно начинать работу и запускать проверки.
