# Статус реализации LLM benchmark

Статус ведётся по плану `LLM_BENCHMARKS_PLAN.md`. Пункт отмечается выполненным
только после реализации, релевантной проверки и подтверждения выходных
артефактов. Вся система benchmark должна размещаться внутри
`app/harness-micro/src/benchmarks`.

## Актуальная граница

Benchmark тестирует только харнесс. Parser, algorithm, metrics, брокер и
межсервисная доставка не являются частью benchmark-run. Харнесс должен
запускаться напрямую внутри процесса по заранее подготовленным локальным
graph/metrics-профилям и source index. Артефакты создаёт и передаёт пользователь;
benchmark проверяет их manifest и целостность, но не запускает их producers.

Ранее реализованные event builder и observable lifecycle через
`HarnessHandler` сохраняются как вспомогательные проверенные компоненты, но не
считаются целевой точкой запуска benchmark и не закрывают прямой runner.

## Сквозные критерии готовности

- [ ] Оба контура проверки работают независимо.
- [ ] Все результаты воспроизводимо связываются с проектом, конфигурацией и
  повтором запуска.
- [ ] Секреты, полный judge prompt и чувствительные payload не попадают в
  отчёты и общие логи.
- [ ] Технические ошибки не оцениваются как обычный ответ низкого качества.
- [ ] Результат судьи валидируется, а спорные решения не принимаются
  автоматически.
- [ ] Итоговый отчёт позволяет вручную сравнить baseline и лучшие варианты.

## Ближайшие задачи

1. Согласовать директорию и формат передачи готового bundle для `import_cycle`,
   затем загрузить предоставленные пользователем graph/metrics-профили.
2. Реализовать прямую benchmark composition Core/Orchestrator с локальными
   каталогами профилей и source index, без брокера и `HarnessHandler`.
3. Перенести technical envelope на прямой запуск и сохранять answer, trace,
   usage и timings по единому `run_id`.
4. Подключить автономное ядро LLM-судьи к результатам технически успешного
   runner, затем откалибровать rubric минимум на 20 вручную размеченных
   findings.
5. После подтверждения вертикального цикла расширить корпус следующими
   синтетическими проектами.

## Выполненные проверки

- Для Этапа 1 полный набор `src/benchmarks/tests` выполнен через `pytest`:
  49 тестов прошли без ошибок и пропусков. Проверены строгая загрузка
  конфигурации, drift production-контрактов, три JSON Schema Draft 2020-12 и
  положительные/отрицательные fixtures. Остаётся одно некритичное
  предупреждение AnyIO о совместимости с будущим pytest 10.
- Для пилота `import_cycle` полный набор `src/benchmarks/tests` выполнен через
  `pytest`: 73 теста прошли без ошибок и пропусков. Адресные проверки
  подтвердили статический цикл импортов, semantic error contract и отклонение
  внешних symlink и реального Windows junction при вычислении digest. Проверены
  реальная карточка, matcher, детерминированный результат и его соответствие
  схеме запуска. Остаётся то же некритичное предупреждение AnyIO.
- Для manifest/staging/event-builder полный набор `src/benchmarks/tests`
  выполнен через `pytest`: 107 тестов прошли без ошибок и пропусков. Адресный
  набор из 56 тестов подтвердил schema, защиту путей и junction/symlink,
  повторную проверку digest, immutable JSON-compatible event и офлайн-проход
  через настоящий `HarnessHandler`. Сеть, LLM и `Core` не запускались.
  Event-builder и handler-pass теперь считаются вспомогательной исторической
  проверкой, а не целевым способом запуска benchmark.
- Для автономного ядра LLM-судьи полный набор `src/benchmarks/tests` выполнен
  через `pytest`: 135 тестов прошли без ошибок и пропусков. Проверены явный
  lifecycle клиента, ограниченные transport retry, строгая JSON Schema
  validation, безопасные технические envelope, три оценки finding и
  majority/median consensus. Live API и калибровка rubric не выполнялись;
  остаётся некритичное предупреждение AnyIO о совместимости с pytest 10.
- Для разрешения эффективной run-конфигурации и profile preflight полный набор
  `src/benchmarks/tests` выполнен через `pytest`: 157 тестов прошли без ошибок и
  пропусков. Адресные 22 теста подтвердили baseline и все однофакторные
  варианты, замену стартовой пары без overview fallback, неизменяемость,
  несекретный детерминированный hash и строгую проверку наличия профилей.
  Остаётся то же некритичное предупреждение AnyIO о совместимости с pytest 10.
- Для offline technical runner полный набор `src/benchmarks/tests` выполнен
  через `pytest`: 269 тестов прошли без ошибок и пропусков. Адресные 138 тестов
  подтвердили строгие статусные инварианты, настоящий lifecycle
  `HarnessHandler`, санитизацию ошибок, противоречия completed event,
  publisher failure после save и безопасное write-once сохранение. Live LLM,
  реальные producer-артефакты и runtime telemetry не использовались. Остаётся
  то же некритичное предупреждение AnyIO о совместимости с pytest 10.
  Этот technical runner проверяет ранее выбранный handler lifecycle; для
  актуальной границы требуется прямой runner без broker-related компонентов.
