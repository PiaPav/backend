# Статус реализации LLM benchmark

Статус ведётся по плану `LLM_BENCHMARKS_PLAN.md`. Пункт отмечается выполненным
только после реализации, релевантной проверки и подтверждения выходных
артефактов. Вся система benchmark должна размещаться внутри
`app/harness-micro/src/benchmarks`.

## Этапы реализации

- [x] **Этап 1. Контракты и структура benchmark**
  - [x] Создать базовую структуру директории `benchmarks`.
  - [x] Описать схемы эталона проекта, результата запуска и решения судьи.
  - [x] Добавить baseline, варианты контекста, toolset и бюджета.
  - [x] Зафиксировать версионирование конфигураций, проектов и prompt судьи.
  - [x] Определить правила хранения локальных запусков без секретов и больших
    сгенерированных артефактов в репозитории.

- [ ] **Этап 2. Синтетические проекты и эталоны**
  - [x] Реализовать пилотный проект `import_cycle` и его строго валидируемую
    машиночитаемую карточку.
  - [ ] Создать проекты `import_cycle`, `complex_function`, `coupled_class` и
    `layer_violation`.
  - [ ] Создать проекты `mixed_project` и `clean_project`.
  - [ ] Подготовить для каждого проекта машиночитаемый `benchmark.yml`.
  - [ ] Получить штатные графовые и метрические профили проектов.
  - [ ] Вручную подтвердить locations, evidence и запрещённые утверждения
    каждой эталонной проблемы.

- [ ] **Этап 3. Детерминированный runner и проверки**
  - [ ] Реализовать подготовку артефактов и входного события харнесса.
    - [x] Реализовать строгую загрузку manifest готового producer export,
      безопасный staging и построение профильного события `harness.start.v1`.
    - [ ] Подключить штатную materialization и реальные producer-артефакты

  - [ ] Реализовать явный выбор стартового контекста, toolset и бюджета.
  - [ ] Запускать анализ штатным путём и сохранять конфигурацию, ответ, trace,

  - [ ] Проверять технический lifecycle, лимиты, tool-контракты, `LLMAnalysis`

  - [ ] Реализовать детерминированное сопоставление findings с эталоном.
    - [x] Для пилота реализовать офлайн-проверки locations, severity,

  - [ ] Откалибровать судью и выделять спорные решения для дополнительной

- [ ] **Этап 5. Baseline и поиск вариантов**
  - [ ] Выполнить baseline по 5 запусков на каждый синтетический проект.
  - [ ] Выполнить однофакторные сравнения бюджетов 2, 4 и 6.

  - [ ] Сравнить контексты `overview`, `compact` и `architecture`.
  - [ ] Отобрать варианты по установленным порогам качества, стоимости,

  - [ ] Сформировать не более четырёх лучших комбинаций и записать их для

- [ ] **Этап 6. Отчёт и ручное решение**

  - [ ] Сформировать сравнение вариантов с baseline и таблицу

  - [ ] Зафиксировать версии параметров после ручного решения.

## Сквозные критерии готовности

- [ ] Оба контура проверки работают независимо.
- [ ] Все результаты воспроизводимо связываются с проектом, конфигурацией и
  повтором запуска.
- [ ] Секреты, полный judge prompt и чувствительные payload не попадают в
  отчёты и общие логи.
- [ ] Технические ошибки не оцениваются как обычный ответ низкого качества.
- [ ] Результат судьи валидируется, а спорные решения не принимаются
  автоматически.
- [ ] Итоговый отчёт позволяет вручную сравнить baseline и лучшие варианты.

## Ближайшие задачи

1. Получить для `import_cycle` штатные graph/metrics-профили и подтвердить по
   ним nodes, import relations и locations карточки без handcrafted-артефактов.
2. Подключить подготовленный manifest/staging/event pipeline к штатному
   `InputMaterializer` и наблюдаемой технической части runner.
3. После подтверждения вертикального цикла расширить корпус следующими
   синтетическими проектами.

## Выполненные проверки

- Для Этапа 1 полный набор `src/benchmarks/tests` выполнен через `pytest`:
  49 тестов прошли без ошибок и пропусков. Проверены строгая загрузка
  конфигурации, drift production-контрактов, три JSON Schema Draft 2020-12 и
  положительные/отрицательные fixtures. Остаётся одно некритичное
  предупреждение AnyIO о совместимости с будущим pytest 10.
- Для пилота `import_cycle` полный набор `src/benchmarks/tests` выполнен через
  `pytest`: 73 теста прошли без ошибок и пропусков. Адресные проверки
  подтвердили статический цикл импортов, semantic error contract и отклонение
  внешних symlink и реального Windows junction при вычислении digest. Проверены
  реальная карточка, matcher, детерминированный результат и его соответствие
  схеме запуска. Остаётся то же некритичное предупреждение AnyIO.
- Для manifest/staging/event-builder полный набор `src/benchmarks/tests`
  выполнен через `pytest`: 107 тестов прошли без ошибок и пропусков. Адресный
  набор из 56 тестов подтвердил schema, защиту путей и junction/symlink,
  повторную проверку digest, immutable JSON-compatible event и офлайн-проход
  через настоящий `HarnessHandler`. Сеть, LLM и `Core` не запускались.
