# План доработки микро-харнесса

## Цель

Перевести харнесс с передачи полного графа и полного набора метрик в стартовом
контексте на управляемое исследование через инструменты. При этом сохранить
текущий сценарий: один запрос анализа, ограниченная сессия LLM и итоговый JSON с
проблемами и сильными сторонами проекта.

План рассчитан на MVP. Он не предполагает отдельный сервис запросов к графу,
базу данных, сложную систему плагинов, потоковый JSON-парсер или универсальный
язык запросов.

## Что не устраивает в текущей реализации

1. Вход содержит только один файл графа и один файл метрик, поэтому инструмент
   не может выбрать профиль по имени.
2. Граф и метрики полностью читаются и отправляются LLM до первого вызова
   инструмента. Это расходует контекст и делает `GET-GRAPH` и `GET-METRICS`
   избыточными.
3. `ToolsEngine` получает только `source_index_path`; для графовых инструментов
   придётся протягивать дополнительные параметры через весь текущий API.
4. Регистрация инструмента распределена между enum, composition root,
   JSON-файлами схем и `Validator`.
5. В `Orchestrator.run_loop` смешаны управление сессией, лимиты, исполнение
   инструментов, обработка причин завершения и финализация. Пограничная логика
   после основного цикла во многом повторяет его ветви.
6. Лимит в три вызова слишком мал для цепочки «найти объект — изучить связи —
   прочитать код — уточнить метрику».
7. Ошибки инструментов и результаты не имеют единого контракта; часть текущих
   ошибок превращается в неинформативный `RuntimeError`.

## Целевой входной контракт

Вместо одиночных `graph` и `metrics` событие должно передавать каталоги
артефактов, где ключом служит точное имя профиля:

```json
{
  "payload": {
    "source_uri": "...",
    "graph_profiles": {
      "parser_semantics_version": 7,
      "graph_fingerprint": "...",
      "artifacts": {
        "canonical.full": {"uri": "...", "sha256": "...", "size_bytes": 0, "schema_version": 1},
        "aggregate.overview": {"uri": "...", "sha256": "...", "size_bytes": 0, "schema_version": 1}
      }
    },
    "metrics_profiles": {
      "metrics_semantics_version": 4,
      "graph_fingerprint": "...",
      "artifacts": {
        "metrics.full": {"uri": "...", "sha256": "...", "size_bytes": 0, "schema_version": 1},
        "metrics.overview": {"uri": "...", "sha256": "...", "size_bytes": 0, "schema_version": 1}
      }
    },
    "source_index": {"uri": "...", "sha256": "...", "size_bytes": 0, "schema_version": 1}
  }
}
```

Поля семантики и fingerprint хранятся на уровне каталога, поскольку относятся
ко всему набору профилей. `graph_fingerprint` графовых и метрических профилей
должен совпадать. Materializer проверяет каждый дескриптор артефакта и
принадлежность всех профилей одному снимку проекта.

Минимально обязательные профили для MVP:

- `canonical.full` — поиск объектов, получение узлов и ссылок;
- `aggregate.overview` — начальное представление графа;
- `metrics.full` — адресное чтение любого раздела метрик;
- `metrics.overview` — начальное представление метрик.

Остальные профили опциональны. Инструмент `GET-GRAPH` или `GET-METRICS`
возвращает понятную ошибку, если запрошенный профиль отсутствует в каталоге.
Харнесс не должен самостоятельно воспроизводить правила материализации из
`algorithm`.

После материализации внутренние модели `MaterializedInputs`, `HarnessRequest` и
`HarnessInputData` должны содержать `dict[str, Path]` для графовых и метрических
профилей вместо двух одиночных путей.

## Контекст анализа и ToolsEngine

Нужно ввести небольшую неизменяемую модель `AnalysisContext`, содержащую:

- пути профилей графа;
- пути профилей метрик;
- путь к индексу исходников;
- идентификатор задачи и проверенные fingerprint снимка.

`ToolsEngine.entry_tool` должен принимать этот контекст, а не отдельный
`source_index_path`. Инструмент получает только контекст текущей задачи и свои
валидированные аргументы.

JSON допустимо загружать целиком при первом обращении и кэшировать на время
задачи: это соответствует масштабу MVP. Кэш должен принадлежать
`AnalysisContext` или task-scoped repository, а не singleton-экземпляру
инструмента, потому что харнесс обрабатывает задачи параллельно.

Для новых инструментов понадобятся простые индексы поверх `canonical.full`:

- `node_id -> node`;
- нормализованное имя -> список узлов;
- kind и filepath -> список узлов;
- исходящие и входящие рёбра по типу связи;
- ссылки по владеющему узлу и статусу разрешения.

Индексы строятся лениво и только один раз на задачу. Отдельное хранилище или
предварительная индексация на диске для MVP не нужны.

## Инструменты

Сигнатуры и пользовательская семантика зафиксированы в `LLM_TOOLS.md`.
Реализацию разумно вести в следующем порядке:

1. Укрепить общую обработку аргументов и ошибок существующих `GET-CONTENT` и
   `GET-STRUCTURE`.
2. Добавить `GET-CODE-RANGE` как безопасный способ читать часть крупного файла.
3. Добавить `FIND-GRAPH-NODES` и `GET-GRAPH-NODE`.
4. Добавить `GET-METRICS-ITEM`.
5. Добавить `GET-GRAPH-SUBGRAPH` и `GET-GRAPH-REFERENCES`.
6. Добавить выдачу целых профилей через `GET-GRAPH` и `GET-METRICS` с общим
   ограничением размера ответа.

Для MVP достаточно ограничений `LIMIT`, максимальной глубины подграфа,
максимального диапазона строк и максимального числа байт результата. Курсоры и
полноценную пагинацию можно отложить: при превышении лимита ответ сообщает
`truncated`, `total` и `returned`, а LLM уточняет запрос.

`ToolsEngine` должен возвращать результат любого инструмента в одной JSON-форме:

```json
{
  "status": "success",
  "profile_id": "calls.topology",
  "result": {},
  "completeness": {
    "truncated": false,
    "total": 1,
    "returned": 1
  },
  "diagnostics": []
}
```

Для инструментов исходного кода `profile_id` равен `null`. Ошибки используют ту
же оболочку со статусом `error`, стабильным кодом, понятным сообщением и
признаком `retryable`. `Orchestrator` помещает эту структуру в tool message без
дополнительной оболочки `status/result`, чтобы не создавать вложенные контракты.

Определение инструмента следует собрать в одном месте: имя, реализация и JSON
Schema аргументов. `Validator` получает список схем из реестра, а composition
root регистрирует тот же список. Динамическая загрузка модулей для MVP не нужна.

## Стартовый prompt

В стартовые сообщения следует включать:

- содержимое `aggregate.overview`;
- содержимое `metrics.overview`;
- перечень доступных графовых и метрических профилей;
- правила интерпретации неполных профилей;
- краткое описание доступных инструментов и лимита вызовов.

`canonical.full` и `metrics.full` в стартовый prompt не помещаются. Они доступны
только через инструменты. Если overview-профиль превышает общий лимит стартового
контекста, задача завершается контролируемой ошибкой входных данных; скрытое
обрезание исходных артефактов недопустимо.

Текст prompt нужно обновить после реализации контрактов, убрав предположение о
том, что полный граф и все метрики всегда находятся в сообщении.

## Упрощение Orchestrator

`Orchestrator` остаётся координатором одной LLM-сессии, но его обязанности нужно
разделить на несколько коротких операций:

- подготовить `AnalysisContext` и стартовые сообщения;
- создать сессию;
- выполнить единый цикл ответов модели;
- исполнить и преобразовать tool calls;
- один раз финализировать результат;
- гарантированно закрыть сессию в `finally`.

Основной цикл должен иметь один путь завершения по лимиту. Отдельный большой
блок обработки «последнего ответа после цикла» следует удалить: при исчерпании
бюджета координатор отправляет результаты последнего допустимого вызова и один
принудительный запрос финального JSON.

Обработку каждого `finish_reason` лучше вынести в небольшие методы, но не нужно
строить универсальный state-machine framework. Для MVP достаточно явного цикла
и перечисления нескольких исходов.

Состояние задачи (`current_iteration`, число tool calls, срок жизни) следует
собрать в одной task-scoped модели. Владение LLM-сессией должно находиться в
одном слое; предпочтительно в `Orchestrator`, а `HarnessRunner` оставить
ответственным только за semaphore и timeout.

Лимиты сообщений и инструментов нужно вынести в конфигурацию. Начальное
значение для MVP — до 6 вызовов инструментов; этого достаточно для одной
осмысленной цепочки проверки без превращения анализа в неограниченный агентный
цикл.

## Технические правила реализации

Этот раздел задаёт ограничения для исполнителя плана. При реализации следует
сначала изучать существующий код затрагиваемого компонента и сохранять его
рабочие соглашения. План не является разрешением переписывать соседние модули,
если изменение их контракта не требуется текущим этапом.

### Общий стиль

- Код должен оставаться прямолинейным: явные условия, небольшие модели и
  обычные вызовы методов предпочтительнее универсальных фреймворков.
- Не вводить слои `use case`, `command bus`, `unit of work`, абстрактные
  repository/factory/provider-классы и контейнер зависимостей только ради
  архитектурной симметрии.
- Новая абстракция оправдана, если у неё есть как минимум два реальных
  потребителя либо она изолирует внешний ввод-вывод, LLM API или формат
  артефакта. Не создавать интерфейс для каждого класса автоматически.
- Внутренние неизменяемые данные оформлять `dataclass` с `slots=True`, когда
  это делает модель проще. Pydantic использовать на внешних границах: входное
  событие, контракт LLM и итоговый JSON.
- Использовать типы Python 3.13 и `Path`, не передавать пути строками между
  внутренними компонентами.
- Имена классов, функций и полей оставлять на английском; пользовательские
  сообщения, документацию и существующий стиль диагностик сохранять на
  русском языке.
- Комментарии должны объяснять причину ограничения или нетривиального решения,
  а не пересказывать строку кода.
- Не выполнять несвязанный рефакторинг и не менять публичные контракты без
  шага совместимости, явно указанного в текущем этапе.

### Границы пакетов

Сохраняется текущее разделение ответственности:

- `harness_service` — приём события, materializer, timeout, ограничение
  параллелизма и composition root;
- `core_server` — сценарий анализа, состояние задачи и координация LLM-сессии;
- `llm_connector` — детали протокола и клиента LLM;
- `tools_engine` — регистрация и исполнение инструментов, чтение артефактов и
  построение task-scoped индексов;
- `infrastructure` — конкретные адаптеры брокера, хранилища и материализации,
  но не правила анализа графа;
- `response_models` — модели внешнего протокола LLM, а не общий склад всех
  внутренних dataclass проекта;
- `rules` — настраиваемые лимиты инструментов и извлечения данных.

Зависимости направляются от composition root к конкретным реализациям и от
логики к небольшим интерфейсам внешних систем. `tools_engine` не должен
импортировать `Orchestrator`, а `llm_connector` не должен знать о графовых
профилях. Связывание выполняется в `harness_service/composition.py`.

При росте числа инструментов допустима следующая раскладка:

```text
tools_engine/
  interface/
    engine.py
    tool.py
  logic/
    engine.py
  models/
    analysis_context.py
    tool_result.py
  accessors/
    graph.py
    metrics.py
    source.py
  tools/
    source/
    graph/
    metrics/
```

`accessors` — простые task-scoped объекты чтения и индексации, а не
универсальный repository layer. Если конкретной группе достаточно одной
функции или небольшого класса, не нужно дополнительно создавать для неё
interface, service и factory. Существующие инструменты можно переносить в
подпакеты только одновременно с обновлением импортов и тестов; сам перенос не
должен становиться отдельным крупным рефакторингом.

### Ошибки и диагностические ответы

Нужно сохранить узнаваемый текущий стиль: собственное исключение содержит
машиночитаемые сведения об ошибке, предоставляет `name` и имеет понятное
строковое представление. При этом новый функционал требует общего контракта:

```text
code       — стабильный строковый код для LLM и тестов;
message    — краткое сообщение на русском языке;
details    — JSON-совместимый словарь с фактическими значениями;
retryable  — может ли LLM исправить аргументы и повторить запрос.
```

Для инструментов базовым остаётся `ToolError`. Достаточно небольшого набора
предметных наследников:

- `InvalidToolArguments`;
- `UnknownTool`;
- `ProfileNotFound`;
- `NodeNotFound`;
- `MetricPathNotFound`;
- `SourceObjectNotFound`;
- `ExtractionLimitExceeded`;
- `InvalidArtifact`.

Не следует создавать отдельный класс для каждого текста ошибки. Если случаи
имеют одинаковую реакцию и отличаются только `code/details`, достаточно одного
типа.

Правила обработки ошибок:

- не использовать пустой `raise` вне `except`, `KeyError` и `ValueError` как
  публичный ответ инструмента;
- отсутствие совпадений в корректном поисковом запросе является успешным
  пустым результатом, а неизвестный конкретный `NODE-ID` — ошибкой;
- ошибки аргументов и отсутствующие объекты обычно `retryable=true`;
- повреждённый или несовместимый материализованный артефакт
  `retryable=false` и завершает текущую задачу;
- `ToolsEngine` преобразует ожидаемые `ToolError` в единый `ToolResult`;
- `Orchestrator` не перечисляет все классы ошибок инструментов и не дублирует
  их форматирование;
- неожиданные исключения логируются на границе задачи и не отправляются LLM со
  stack trace или внутренними путями;
- ошибки провайдера и жизненного цикла сессии остаются наследниками
  `HarnessError` и не смешиваются с ошибками инструментов.

### Работа с артефактами и путями

- Профиль извлекается только из проверенного словаря `profile_id -> Path`.
  Нельзя строить путь к файлу непосредственной подстановкой `PROFILE-ID`.
- Исходный файл открывается только после проверки его относительного пути по
  `source_index` и принадлежности материализованному корню проекта.
- `METRIC-PATH` разбирается как JSON Pointer без `eval`, выражений Python и
  самодельного языка запросов.
- Fingerprint и версии семантики проверяются materializer до запуска LLM.
  Инструменты не повторяют эту проверку при каждом вызове.
- Полные JSON-профили загружаются лениво и не более одного раза на задачу.
  Между задачами содержимое и индексы не разделяются.
- Чтение крупных файлов и построение индексов не должно надолго блокировать
  event loop. Для MVP достаточно выполнить синхронную работу через
  `asyncio.to_thread`; переводить весь проект на асинхронный файловый API не
  нужно.
- Лимит результата применяется после сериализации ответа. При допустимой
  обрезке возвращаются `truncated`, `total` и `returned`; нельзя молча обрезать
  JSON посередине.

### Инструменты и схемы

- У каждого инструмента один класс реализации и одна JSON Schema аргументов.
  Имя, schema и класс связываются одной записью реестра.
- Проверка обязательных полей выполняется до преобразования в `Path`, enum или
  число, чтобы отсутствие аргумента не превращалось в случайный `TypeError`.
- Строковые enum (`KIND`, `DIRECTION`, `STATUS`, тип связи) перечисляются в
  schema и дополнительно валидируются внутри харнесса.
- Результаты сортируются детерминированно. Одинаковый снимок и одинаковые
  аргументы должны давать одинаковый порядок элементов.
- `GET-GRAPH-NODE` и `FIND-GRAPH-NODES` используют `canonical.full` как
  канонический источник. Специализированный профиль не должен менять
  идентичность узла.
- Позиционные таблицы метрик `$columns/$rows` при адресной выдаче желательно
  преобразовывать в объекты с именованными полями, не изменяя исходный
  артефакт.
- Не добавлять скрытые эвристики автоматического выбора профиля. Если профиль
  не указан или недоступен, ответ должен прямо это сообщать.

### Orchestrator и жизненный цикл

- В `Orchestrator` должен остаться один основной цикл и один путь принудительной
  финализации после исчерпания бюджета.
- Создание и закрытие LLM-сессии принадлежат одному компоненту и защищаются
  `try/finally`.
- `HarnessRunner` отвечает за semaphore и общий timeout, но не исправляет
  внутреннее состояние `Orchestrator` после его ошибок.
- Счётчики изменяются в одном месте: вызов инструмента учитывается после
  принятия tool call, а число итераций — после завершённого обмена с LLM.
- Несколько tool calls в одном ответе обрабатываются в исходном порядке. Для
  MVP не требуется их параллельное исполнение.
- Финальная валидация через `LLMAnalysis` и запрет инструментов в финальном
  запросе сохраняются.
- Retry провайдера должен быть ограничен конфигурацией и не расходовать бюджет
  инструментов.

### Логирование

- Сохранить существующий структурированный подход с `unique_id`, `event` и
  `description`.
- Логировать имя инструмента, профиль, статус, длительность и размеры
  `returned/total`, но не полное содержимое исходников, графов и метрик.
- Не записывать API-ключи, URI с секретами, полный prompt и stack trace в
  сообщение, которое может получить LLM.
- Не добавлять отдельную систему tracing для MVP; достаточно текущего logger и
  нескольких согласованных событий.

### Тесты и критерий готовности

- Unit-тесты инструментов используют небольшие локальные JSON-фикстуры и
  временный каталог исходников. В тестах не должно быть абсолютных путей к
  соседнему репозиторию `algorithm`.
- Тесты `Orchestrator` работают с fake session и fake tools engine; живой LLM
  API не нужен.
- Для входного контракта проверяются точные поля, совпадение fingerprint,
  обязательные профили и временная совместимость со старым форматом.
- Для ошибок проверяются `code`, `retryable`, безопасные `details` и итоговый
  JSON tool message, а не только факт исключения.
- Этап считается завершённым, когда реализованы его пункты, обновлены
  относящиеся к ним тесты, выполнены релевантные проверки и обновлён
  `HARNESS_REWORK_PLAN_STATUS.md`.
- Не отмечать этап выполненным за счёт заглушек, отключённых тестов или
  незарегистрированных инструментов.

### Ограничения для будущей LLM

При работе по этому плану LLM должна брать один этап или явно связанный набор
пунктов, сначала изучать соответствующие файлы, затем вносить минимальный
законченный diff. Нельзя заранее реализовывать отложенные возможности, менять
весь проект под новую архитектурную модель или заменять понятный код
метапрограммированием ради уменьшения числа строк.

Если фактическая схема Graph DTO или Metrics DTO не позволяет реализовать
описанный запрос однозначно, нужно остановить реализацию конкретного
инструмента, описать расхождение контракта и запросить решение. Нельзя угадывать
поля, типы связей или семантику статусов по названию.

## Этапы реализации

### Этап 1. Контракты и совместимость

- описать новые event-модели каталогов профилей;
- обновить materializer и внутренние входные dataclass;
- добавить `AnalysisContext`;
- на период перехода при необходимости принимать старый формат и превращать
  его в одноэлементные каталоги, но не обещать выбор отсутствующих профилей.

### Этап 2. Основа инструментов

- единый реестр и схемы аргументов;
- единый результат и типизированные ошибки;
- общие лимиты размера;
- исправление обработки неверных аргументов в существующих инструментах.

### Этап 3. Новые инструменты

- инструменты исходного кода;
- поиск и чтение узлов;
- адресное чтение метрик;
- подграфы, ссылки и выдача профилей.

Каждый инструмент сопровождается unit-тестами на успешный ответ, неизвестный
идентификатор, неверные аргументы и обрезку результата.

### Этап 4. Orchestrator и prompt

- заменить текущий дублирующийся цикл;
- перевести стартовый контекст на overview-профили;
- увеличить и конфигурировать бюджет инструментов;
- проверить обязательную финализацию и закрытие сессии.

### Этап 5. Сквозная проверка

- обработать событие с минимальным набором обязательных профилей;
- выполнить цепочку поиска узла, получения подграфа, чтения исходника и метрики;
- проверить отсутствующий опциональный профиль;
- проверить лимит ответа инструмента и лимит всей сессии;
- убедиться, что итоговый ответ по-прежнему проходит `LLMAnalysis`.

## Что сознательно отложено. Не пытаться реализовать!

- удалённый API запросов к графу и метрикам;
- база данных или постоянный индекс графа;
- универсальный query language;
- потоковая обработка больших JSON;
- курсорная пагинация;
- автоматический выбор или построение отсутствующего профиля;
- параллельное исполнение зависимых tool calls;
- сложная система оценки токенов каждого результата.

К этим задачам стоит возвращаться только после измерения размеров реальных
проектов и поведения LLM на MVP.
