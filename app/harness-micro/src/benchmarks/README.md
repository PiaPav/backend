# LLM benchmark

Пакет содержит изолированную benchmark-систему харнесса. Продуктовые пакеты не
должны содержать специальных ветвей для benchmark; последующие runner и
evaluator используют публичные контракты харнесса.

## Контракты Этапа 1

- `config.py` строго загружает несекретные YAML-конфигурации без import-time I/O;
- `configs/` фиксирует baseline, однофакторные варианты, анализирующую модель и
  отключённую по умолчанию конфигурацию судьи;
- `schemas/` содержит JSON Schema Draft 2020-12 для карточки проекта, результата
  запуска и решения судьи;
- `prompts/judge.md` — версия `0.1.0`, статус `uncalibrated`;
- `runs/` предназначен только для локальных результатов и игнорируется Git.

## Пилот Этапов 2–3

- `projects/import_cycle/` содержит первый синтетический проект и карточку
  `benchmark.yml` с подтверждаемым по исходникам циклом импортов;
- `project.py` строго загружает карточку, проверяет межполевые инварианты,
  существование locations и вычисляет воспроизводимый digest проекта;
- `evaluators/matcher.py` формирует только кандидатов соответствия по точному
  location и лексическому meaning, не выставляя семантический verdict;
- `evaluators/deterministic.py` офлайн проверяет locations, порядок severity,
  буквальные запрещённые утверждения и точные дубликаты findings.
- `artifact_manifest.schema.json` и `artifacts.py` строго проверяют локальный
  export штатного producer, его fingerprints, размеры, SHA-256 и безопасные
  пути, после чего копируют его в отдельный staging-каталог;
- `event.py` и `runners/prepare_input.py` формируют детерминированное профильное
  событие `harness.start.v1`, совместимое с публичным `HarnessHandler`, но не
  запускают LLM или `Core`.

Штатные graph/metrics-артефакты пилота ещё не зафиксированы и не подменяются
написанными вручную fixtures. Поэтому весь Этап 2 и полный runner Этапа 3 пока
не считаются завершёнными.

Manifest описывает уже готовый producer export и не доказывает его
происхождение. Staging не изменяет source index и не интерпретирует содержимое
graph/metrics DTO: полную materialization и проверку DTO выполняет штатный
`InputMaterializer` при реальном запуске.

## Автономное ядро Этапа 4a

- `evaluators/judge_client.py` реализует явный async lifecycle, ограниченные
  повторы только транспортных сбоев и строгую проверку ответа по judge schema;
- `evaluators/judge.py` формирует минимальный двухсообщенческий запрос,
  последовательные повторные оценки и консервативный majority consensus;
- unit-тесты используют только инъецируемый offline transport: live API не
  вызывается и ключи не записываются в результаты;
- этап не включает calibration судьи и integration с benchmark runner. Rubric
  остаётся `uncalibrated`.

## Версионирование

- schema-контракты используют целочисленный `schema_version`; несовместимое
  изменение повышает major-версию схемы;
- конфигурации, проекты и prompts используют SemVer;
- каждый prompt хранится вместе с SHA-256, а результат запуска должен содержать
  hash разрешённой конфигурации, карточки проекта и использованных prompts;
- изменение исходников проекта или эталонных findings требует новой версии
  проекта; после первого запуска смысл существующего baseline не меняется
  молча;
- judge rubric остаётся в `0.x` и `uncalibrated`, пока вручную не размечено и не
  проверено не менее 20 findings.

## Секреты и результаты

- API key передаётся только через имя переменной окружения из конфигурации;
- ключи, environment dumps, полный judge prompt и чувствительные payload не
  сохраняются в сводных результатах или общих логах;
- один запуск хранится в отдельной неизменяемой директории `runs/<run_id>/`;
- большие профили и tool payload не копируются в сводный JSON; raw judge answer
  допустим только в локальной директории конкретного запуска;
- в репозитории допускаются только небольшие проверяемые fixtures и исходники
  синтетических проектов.

## Проверка

Из `app/harness-micro`:

```text
.venv/Scripts/python.exe -m pytest src/benchmarks/tests -q
```

Тесты требуют `pytest`, `PyYAML` и `jsonschema`.
