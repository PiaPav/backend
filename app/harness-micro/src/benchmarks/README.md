# LLM benchmark

Пакет содержит изолированную benchmark-систему харнесса. Продуктовые пакеты не
должны содержать специальных ветвей для benchmark; последующие runner и
evaluator используют публичные контракты харнесса.

## Контракты Этапа 1

- `config.py` строго загружает несекретные YAML-конфигурации без import-time I/O;
- `configs/` фиксирует baseline, однофакторные варианты, анализирующую модель и
  отключённую по умолчанию конфигурацию судьи;
- `schemas/` содержит JSON Schema Draft 2020-12 для карточки проекта, результата
  запуска и решения судьи;
- `prompts/judge.md` — версия `0.1.0`, статус `uncalibrated`;
- `runs/` предназначен только для локальных результатов и игнорируется Git.

## Версионирование

- schema-контракты используют целочисленный `schema_version`; несовместимое
  изменение повышает major-версию схемы;
- конфигурации, проекты и prompts используют SemVer;
- каждый prompt хранится вместе с SHA-256, а результат запуска должен содержать
  hash разрешённой конфигурации, карточки проекта и использованных prompts;
- изменение исходников проекта или эталонных findings требует новой версии
  проекта; после первого запуска смысл существующего baseline не меняется
  молча;
- judge rubric остаётся в `0.x` и `uncalibrated`, пока вручную не размечено и не
  проверено не менее 20 findings.

## Секреты и результаты

- API key передаётся только через имя переменной окружения из конфигурации;
- ключи, environment dumps, полный judge prompt и чувствительные payload не
  сохраняются в сводных результатах или общих логах;
- один запуск хранится в отдельной неизменяемой директории `runs/<run_id>/`;
- большие профили и tool payload не копируются в сводный JSON; raw judge answer
  допустим только в локальной директории конкретного запуска;
- в репозитории допускаются только небольшие проверяемые fixtures и исходники
  синтетических проектов.

## Проверка

Из `app/harness-micro`:

```text
.venv/Scripts/python.exe -m pytest src/benchmarks/tests -q
```

Тесты требуют `pytest`, `PyYAML` и `jsonschema`.
