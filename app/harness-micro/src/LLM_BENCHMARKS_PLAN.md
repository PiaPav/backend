# План продуктового тестирования LLM-харнесса

## 1. Цель

Создать простой воспроизводимый benchmark для проверки двух свойств харнесса:

1. харнесс технически корректно проводит анализ по готовым входным данным;
2. внешняя LLM находит подтверждённые проблемы с приемлемыми качеством,
   стабильностью и стоимостью.

Benchmark предназначен для MVP. Он не должен превращаться в универсальную
платформу тестирования моделей, распределённую систему запусков или сложный
набор статистических исследований.

## 2. Обязательная граница реализации

Вся будущая реализация benchmark-системы должна находиться только в директории:

```text
app/harness-micro/src/benchmarks
```

Продуктовый код харнесса не следует смешивать с кодом benchmark. Benchmark
может импортировать публичные компоненты харнесса, загружать заранее
подготовленные входные артефакты и вызывать харнесс напрямую, но не должен
добавлять тестовые условия в `core_server`, `harness_service`, `tools_engine`
или другие продуктовые пакеты.

Benchmark проверяет только харнесс. Построение графа, расчёт метрик, работа
parser/algorithm/metrics, брокера, consumer, publisher и межсервисной доставки
не входят в предмет проверки. Запуск выполняется внутри процесса через прямую
точку входа харнесса, без broker event, `HarnessHandler`, idempotency store и
публикации completion event.

Графовые и метрические профили для тестовых проектов создаются заранее вне
benchmark-run. Пользователь размещает готовые артефакты в согласованной
директории проекта или передаёт путь к локальному bundle. Benchmark обязан
проверить manifest, версии, hashes, fingerprints, наличие требуемых профилей и
безопасность путей, но не обязан доказывать происхождение артефактов и не
запускает сервисы, которые их построили.

Предварительная структура:

```text
benchmarks/
  README.md
  config.py
  configs/
    baseline.yml
    variants.yml
    models.yml
    judge.yml
  projects/
    import_cycle/
      project/
      benchmark.yml
    complex_function/
      project/
      benchmark.yml
    coupled_class/
      project/
      benchmark.yml
    layer_violation/
      project/
      benchmark.yml
    mixed_project/
      project/
      benchmark.yml
    clean_project/
      project/
      benchmark.yml
  schemas/
    benchmark.schema.json
    run_result.schema.json
    judge_result.schema.json
  prompts/
    judge.md
  runners/
    prepare_artifacts.py
    run_benchmark.py
  evaluators/
    deterministic.py
    matcher.py
    judge_client.py
    judge.py
    aggregate.py
  reports/
    build_report.py
  tests/
  runs/
```

`runs/` предназначена для локальных результатов запусков и не должна содержать
ключи API или иные секреты. Большие сгенерированные артефакты и результаты не
следует хранить в репозитории без отдельного решения.

## 3. Общая схема проверки

Проверка делится на два независимых контура.

### 3.1. Контур A — детерминированная проверка харнесса

Контур отвечает на вопрос: «Харнесс технически выполнил задачу правильно?»

Для каждого запуска автоматически проверяются:

- прямой вход харнесса собран из заранее подготовленного source index и
  каталогов профилей;
- обязательные профили графа и метрик присутствуют и прошли preflight;
- LLM-сессия создана и закрыта;
- стартовый контекст соответствует выбранной конфигурации;
- модели доступны только разрешённые инструменты;
- лимиты итераций и инструментов не нарушены;
- tool calls и результаты инструментов имеют валидный контракт;
- финальный ответ проходит `LLMAnalysis`;
- финальный результат получен и сохранён benchmark runner;
- в логах присутствуют события основных ветвей оркестратора;
- в DB-метаданных присутствуют `model`, `id`, `usage` и `finish_reason`, когда
  провайдер их возвращает;
- в логах отсутствуют prompt, исходники, аргументы и полные результаты
  инструментов, секреты и stack trace;
- записаны длительность, число вызовов, token usage, повторы провайдера и
  причина финализации.

Результат контура: `passed`, `failed` или `infrastructure_error` с перечнем
нарушенных проверок. Ошибка этого контура считается дефектом системы и не
передаётся LLM-судье как обычный ответ низкого качества.

### 3.2. Контур B — вероятностная оценка качества LLM

Контур выполняется только для технически успешных запусков и отвечает на
вопрос: «Насколько хорошо LLM разобралась в проекте?»

Проверяются:

- обнаружение заложенных проблем;
- отсутствие неподтверждённых проблем;
- корректность категории и severity;
- корректность location;
- качество и достаточность evidence;
- практичность recommendation;
- отсутствие преувеличений и недоказанных runtime-утверждений;
- стабильность результатов между повторными запусками.

Технический success rate и качество успешных ответов должны выводиться
раздельно.

## 4. Набор синтетических проектов MVP

На первом этапе создаются шесть небольших проектов.

### 4.1. `import_cycle`

Содержит подтверждённый цикл импортов между двумя пакетами. Проверяет поиск
зависимостей, корректность location и отсутствие ложного утверждения, что цикл
обязательно приводит к runtime-сбою.

### 4.2. `complex_function`

Содержит одну чрезмерно большую функцию с высокой цикломатической и когнитивной
сложностью, глубокой вложенностью и несколькими обязанностями. Проверяет связь
метрик с конкретным исходным кодом.

### 4.3. `coupled_class`

Содержит класс с высокой связностью с внешними компонентами, большим WMC/RFC и
низкой внутренней связностью. Проверяет совместное использование объектных
метрик, графа вызовов и исходников.

### 4.4. `layer_violation`

Содержит явную обратную зависимость: инфраструктурный или нижний слой импортирует
верхний прикладной слой. Проверяет понимание направления зависимости, а не
только наличие импортов.

### 4.5. `mixed_project`

Содержит три проблемы разных типов и несколько нормальных компонентов. Проверяет
приоритизацию и способность уложиться в ограниченный бюджет инструментов.

### 4.6. `clean_project`

Не содержит намеренно внесённых существенных проблем. Допускаются небольшие
стилистические несовершенства, но они не должны выдаваться за архитектурные
дефекты. Проект нужен для измерения false positive и hallucination rate.

Проекты должны быть достаточно малы для быстрого построения артефактов, но не
сводиться к одному очевидному файлу. Каждый дефект должен быть доступен
статическому анализу и не требовать запуска проекта.

Для каждого проекта рядом с эталоном фиксируется ожидаемый набор заранее
подготовленных graph/metrics-профилей. Эти файлы являются входными fixtures
харнесса, а не объектом оценки parser или metrics. Ошибка их загрузки считается
ошибкой benchmark-инфраструктуры, но содержательная корректность генераторов
артефактов данным benchmark не оценивается.

## 5. Эталон проекта

Каждый проект содержит `benchmark.yml` с машиночитаемым эталоном.

Обязательные поля:

```yaml
project_id: import_cycle
description: Краткое назначение проекта

expected_findings:
  - id: ISSUE-001
    category: dependency_cycle
    severity_min: medium
    severity_max: high
    locations:
      - package_a/service.py
      - package_b/repository.py
    evidence:
      nodes:
        - package_a.service
        - package_b.repository
      relations:
        - imports
    acceptable_meanings:
      - циклическая зависимость
      - взаимный импорт пакетов
    required_data:
      graph: true
      metrics: false
      source: optional
    forbidden_claims:
      - runtime deadlock
      - data corruption

additional_findings_policy: require_evidence
```

Эталон фиксирует известные проблемы, но не объявляется исчерпывающим. Новое
замечание LLM оценивается как:

- подтверждённая дополнительная проблема;
- спорное замечание;
- неподтверждённое замечание;
- явная галлюцинация.

Новые подтверждённые проблемы после ручной проверки добавляются в следующую
версию эталона.

## 6. Стартовая конфигурация benchmark

Исходной точкой является конфигурация, наиболее близкая к текущему production
сценарию.

### 6.1. Baseline

- системный prompt: текущий `prompts/PROMPT.md` без изменений;
- стартовый граф: `aggregate.overview`;
- стартовые метрики: `metrics.overview`;
- в каталоге доступны обязательные `canonical.full` и `metrics.full`;
- набор инструментов: все зарегистрированные инструменты;
- бюджет инструментов: 6;
- лимит итераций: текущее production-значение;
- модель: текущая основная production-модель;
- temperature и остальные параметры: фиксированные и записанные в
  конфигурации; если параметр провайдером не поддерживается, это явно
  фиксируется;
- число запусков: 5 на каждый синтетический проект.

Baseline запускается первым и служит точкой сравнения всех вариантов.

## 7. Варианты конфигурации

Полный декартов перебор не выполняется. На первом этапе меняется только один
фактор относительно baseline.

### 7.1. Бюджет инструментов

Проверяются значения:

- 2 — минимальное короткое исследование;
- 4 — промежуточный вариант;
- 6 — baseline.

Значения выше 6 в MVP не исследуются. К ним можно вернуться только при наличии
доказанного дефицита бюджета.

### 7.2. Набор инструментов

Проверяются четыре набора:

1. `full` — все инструменты, baseline;
2. `targeted` — полный набор без `GET-GRAPH` и `GET-METRICS`, чтобы проверить,
   достаточно ли адресных запросов без дорогой выдачи целого профиля;
3. `without_source` — без `GET-CONTENT`, `GET-CODE-RANGE` и `GET-STRUCTURE`,
   чтобы измерить ценность проверки исходников;
4. `without_relations` — без `GET-GRAPH-SUBGRAPH` и
   `GET-GRAPH-REFERENCES`, чтобы измерить ценность исследования связей.

Эти варианты являются benchmark-конфигурациями и не меняют production-реестр.

### 7.3. Стартовый контекст

Проверяются три осмысленных варианта:

1. `overview` — `aggregate.overview` + `metrics.overview`, baseline;
2. `compact` — `inventory.minimal` + `metrics.aggregate`;
3. `architecture` — `aggregate.packages` + `metrics.architecture`.

Полные `canonical.full` и `metrics.full` не помещаются в стартовый prompt ни в
одном варианте и остаются доступны только через инструменты.

Для поддержки вариантов benchmark runner должен выбирать явно указанные
профили. Автоматическое построение отсутствующего профиля и скрытый fallback
запрещены. Если текущий production-контракт допускает только overview-пару,
поддержка выбора контекста реализуется внутри benchmark-обвязки или через
явную конфигурационную точку, а не через подмену артефактов под неверными ID.
Runner выбирает профили только из заранее загруженного локального каталога и не
обращается для их построения к parser, algorithm или metrics.

### 7.4. Модель

В MVP используется одна production-модель. Вторая анализирующая модель
добавляется только после выбора разумной конфигурации контекста, инструментов и
бюджета. Это не позволяет смешать влияние модели с влиянием харнесса на первом
этапе.

## 8. Порядок поиска лучшей конфигурации

### Шаг 1. Baseline

Запустить baseline 5 раз на каждом проекте. Получить исходные качество,
стабильность, стоимость и технический success rate.

### Шаг 2. Однофакторное сравнение

Каждый вариант бюджета, toolset и контекста запустить по 3 раза на каждом
проекте. В каждом сравнении изменяется только один фактор.

### Шаг 3. Отбор значимых вариантов

Вариант считается перспективным, если выполняется хотя бы одно условие:

- качество выросло минимум на 5 процентных пунктов без роста стоимости более
  чем на 20%;
- стоимость снизилась минимум на 10%, а качество снизилось не более чем на
  2 процентных пункта;
- detection rate проблемы класса `high` вырос минимум на 10 процентных
  пунктов;
- технический success rate заметно улучшился.

Порог используется как правило отбора MVP, а не как доказательство
статистической значимости.

### Шаг 4. Ограниченные комбинации

Сформировать не более четырёх комбинаций из лучших вариантов. Например:

- лучший контекст + бюджет 4 + `full`;
- лучший контекст + бюджет 6 + `targeted`;
- baseline-контекст + лучший toolset + бюджет 4;
- baseline целиком как контроль.

Данные комбинации записываются в выходной файл как лучшие варианты, требующие
ручного просмотра. На этом поиск завершается.

## 9. Детерминированное сопоставление результата

Перед использованием LLM-судьи выполняются простые проверки:

- JSON соответствует `LLMAnalysis`;
- число issues/strengths соответствует контракту;
- location существует в проекте или равен `null`;
- упомянутые файлы и объекты существуют;
- severity допустим;
- finding сопоставляется с эталоном по category, location и ключевым evidence;
- отсутствуют явно запрещённые утверждения;
- найденные проблемы не дублируются внутри ответа.

Детерминированный matcher формирует кандидатов соответствия
`finding -> expected_finding`, но не принимает окончательное решение при
неоднозначной формулировке.

## 10. Система LLM-судьи

### 10.1. Техническая реализация

Общение с внешней LLM-судьёй следует реализовать по тому же общему принципу,
который уже используется харнессом: отдельный клиент получает настройки
провайдера, подключается к внешнему API, отправляет сообщения и преобразует
ответ провайдера во внутреннюю модель. При этом судье не нужны `Orchestrator`,
инструменты и многошаговая сессия.

Для MVP достаточно одного прямолинейного асинхронного класса
`LLMJudgeClient` в `benchmarks/evaluators/judge_client.py` со следующими
операциями:

- `connect()` — создать и проверить HTTP-клиент;
- `evaluate(messages)` — отправить ровно один запрос и вернуть один ответ;
- `close()` — освободить соединение;
- поддержать использование через async context manager, чтобы соединение
  закрывалось и при ошибке.

Один вызов `evaluate()` соответствует одной оценке одного finding. Три
повторные оценки организует `benchmarks/evaluators/judge.py`, трижды вызывая
клиент и сохраняя каждый ответ отдельно. Сам клиент не должен содержать
агентный цикл, память между оценками или вызовы инструментов.

Запрос состоит из двух сообщений:

1. system message с фиксированной rubric из `benchmarks/prompts/judge.md`;
2. user message с JSON-объектом, содержащим finding, подходящие эталонные
   карточки и только релевантные evidence.

Если провайдер поддерживает JSON Schema или JSON mode, его необходимо включить.
Полученный ответ сначала разбирается как JSON, затем валидируется по
`judge_result.schema.json`. Невалидный ответ не исправляется эвристиками и
помечается как `judge_error`. Для MVP допустимы не более двух повторов только
при сетевой ошибке или перегрузке провайдера; семантически невалидный ответ
повторно не запрашивается автоматически.

Настройки судьи должны быть независимы от настроек анализирующей модели и
загружаться через `benchmarks/config.py` аналогично подходу
`utils/config.py`: типизированная dataclass-модель, YAML для несекретных
локальных параметров и переменные окружения для секретов. Минимальный набор
полей:

```yaml
judge:
  url: "https://provider.example/v1"
  model: "judge-model"
  temperature: 0.1
  timeout_seconds: 120
  max_transport_retries: 2
```

API key передаётся только через переменную окружения, имя которой указывается
в конфигурации, либо через отдельное локальное окружение. Ключ нельзя сохранять
в `judge.yml`, результатах запусков или логах. Значения `url`, `model`,
temperature, timeout и версия judge prompt записываются в результат benchmark.

Клиент должен сохранять для каждого запроса технические сведения:

- статус запроса и тип ошибки;
- model и response ID;
- token usage;
- длительность;
- номер повторной оценки finding;
- число транспортных повторов.

Полный prompt судьи и API key в общие логи не записываются. Исходный JSON-ответ
можно хранить в файле конкретного benchmark-run, поскольку он необходим для
аудита оценки, но он не должен попадать в краткий сводный отчёт.

По возможности модель-судья должна отличаться от анализирующей модели. Если в
MVP используется тот же провайдер или та же модель, это явно фиксируется в
отчёте как ограничение эксперимента.

### 10.2. Назначение

LLM-судья используется только для семантических вопросов:

- описывает ли finding ту же проблему, что и эталон;
- достаточно ли evidence;
- соответствует ли severity доказательствам;
- нет ли недоказанных выводов;
- является ли новое замечание реальной дополнительной проблемой.

### 10.3. Вход судьи

Судья получает:

- один finding анализирующей модели;
- одну или несколько подходящих эталонных карточек;
- только релевантные фрагменты исходника, графа и метрик;
- фиксированную rubric;
- запрет использовать знания вне переданных доказательств.

Судья не получает имя анализирующей модели, стоимость запуска, вариант
конфигурации и информацию о том, является ли ответ baseline.

### 10.4. Формат решения

Судья возвращает строгий JSON:

```json
{
  "matched_issue_id": "ISSUE-001",
  "verdict": "confirmed",
  "category_score": 2,
  "location_score": 2,
  "evidence_score": 3,
  "severity_score": 2,
  "recommendation_score": 2,
  "unsupported_claims": [],
  "confidence": 0.9
}
```

Допустимые verdict: `confirmed`, `partial`, `unsupported`, `novel`, `abstain`.

### 10.5. Повторные оценки

Для каждого finding выполняются три вызова одного судьи с одинаковой rubric и
низкой temperature. Итог определяется большинством verdict и медианой числовых
оценок.

Эти вызовы считаются повторной выборкой одного оценщика, а не тремя полностью
независимыми экспертами. В MVP этого достаточно. Вторую модель-судью следует
добавлять только для случаев:

- три решения не дали большинства;
- confidence ниже установленного порога, например 0.7;
- finding отмечен как `novel`;
- результат существенно влияет на выбор production-конфигурации.

Оставшиеся расхождения передаются человеку.

### 10.6. Калибровка

Перед массовым использованием вручную размечаются не менее 20 findings:
правильные, частично правильные, ложные и содержащие преувеличения. Prompt судьи
корректируется до приемлемого совпадения с этой разметкой, после чего его версия
фиксируется.

## 11. Метрики

### 11.1. Основные метрики качества

- `weighted_recall` — доля найденных эталонных проблем с учётом severity;
- `precision` — доля подтверждённых findings;
- `false_positive_rate` на чистом проекте;
- `hallucination_rate` — доля findings с выдуманными объектами, связями или
  недоказанными утверждениями;
- `location_accuracy`;
- `evidence_score`;
- `severity_accuracy`;
- detection rate каждой эталонной проблемы по повторным запускам.

Вес эталонных проблем для MVP:

- critical — 4;
- high — 3;
- medium — 2;
- low — 1.

### 11.2. Сводная оценка

Для сортировки конфигураций используется вспомогательный `quality_score`:

```text
45% weighted_recall
25% precision
15% normalized evidence score
10% location accuracy
5% normalized recommendation score
```

Сводная оценка не заменяет отдельные показатели. Конфигурация с высоким score,
но неприемлемым hallucination rate не может быть выбрана.

### 11.3. Стоимость и эксплуатационные показатели

- prompt, completion и cache tokens;
- стоимость одного запуска;
- длительность;
- число tool calls;
- число ошибок инструментов;
- число provider retries;
- стоимость одной подтверждённой проблемы;
- `quality_score` на единицу стоимости;
- доля технически успешных запусков.

## 12. Формат результатов запуска

Каждый запуск сохраняет отдельный структурированный результат:

```json
{
  "run_id": "...",
  "project_id": "import_cycle",
  "configuration_id": "baseline",
  "model": "...",
  "prompt_version": "...",
  "context_variant": "overview",
  "toolset_variant": "full",
  "tool_budget": 6,
  "repeat": 1,
  "technical_result": {},
  "llm_analysis": {},
  "deterministic_evaluation": {},
  "judge_evaluations": [],
  "aggregated_evaluation": {},
  "usage": {},
  "timings": {}
}
```

Trace инструментов связывается с `run_id`, но большие результаты инструментов
не копируются в сводный файл.

## 13. Итоговый отчёт

Для каждой конфигурации отчёт должен показывать:

- число запусков и technical success rate;
- средний и медианный quality score;
- разброс результатов;
- weighted recall, precision и hallucination rate;
- detection rate по каждой эталонной проблеме;
- среднюю стоимость, token usage и длительность;
- среднее число tool calls;
- стоимость подтверждённой проблемы;
- сравнение с baseline;
- перечень случаев, переданных человеку.

Рекомендуемый итог — таблица конфигураций и график «качество — стоимость».

## 14. Этапы реализации

### Этап 1. Контракты benchmark

- создать директорию `benchmarks` и базовую структуру;
- зафиксировать схемы `benchmark.yml`, результата запуска и решения судьи;
- создать `baseline.yml` и `variants.yml`;
- определить версионирование проектов, prompt и judge rubric.

### Этап 2. Синтетические проекты

- создать шесть проектов MVP;
- подготовить для каждого `benchmark.yml`;
- принять и разместить заранее созданные пользователем графовые и метрические
  профили для каждого проекта;
- проверить manifest, hashes, fingerprints, версии и наличие всех профилей,
  необходимых baseline и вариантам;
- вручную проверить, что эталонные evidence присутствуют в артефактах.

### Этап 3. Детерминированный runner

- реализовать загрузку локального bundle и сборку прямого входа харнесса;
- реализовать выбор context/toolset/budget;
- создавать benchmark composition харнесса и запускать его напрямую внутри
  процесса, без брокера, transport handler и completion event;
- сохранять run result и технические показатели;
- реализовать детерминированные проверки и matcher.

### Этап 4. LLM-судья

- добавить отдельную dataclass-конфигурацию судьи в `benchmarks/config.py`;
- вынести несекретные параметры подключения в `configs/judge.yml`, а API key —
  в переменную окружения;
- реализовать простой `LLMJudgeClient` с методами `connect`, `evaluate` и
  `close`, где один вызов `evaluate` выполняет один запрос к внешнему API и
  получает один ответ;
- добавить ограниченные транспортные retry и гарантированное закрытие клиента;
- написать и откалибровать `prompts/judge.md`;
- формировать system message из judge prompt и user message из finding,
  эталонных карточек и релевантных evidence;
- реализовать строгую JSON-валидацию решения;
- выполнять три независимых вызова клиента для каждого finding и сохранять
  ответы раздельно;
- агрегировать majority/median;
- сохранять model, response ID, token usage, длительность и ошибки каждого
  вызова без записи API key и полного prompt в общие логи;
- отмечать случаи для второй модели или человека.

### Этап 5. Baseline и варианты

- выполнить baseline;
- выполнить однофакторные варианты;
- выбрать не более четырёх комбинаций;
- записать выбранные комбинации в выходной файл как варианты для ручного
  просмотра и завершить автоматический поиск.

### Этап 6. Отчёт и решение

- сформировать итоговую таблицу качества и стоимости;
- проверить спорные и novel findings вручную;
- подготовить данные для ручного выбора production-кандидата либо сохранения
  baseline;
- после ручного решения зафиксировать версии всех параметров выбранной
  конфигурации.

## 15. Критерии готовности MVP benchmark

План считается реализованным, когда:

- все файлы системы находятся в `app/harness-micro/src/benchmarks`;
- доступны шесть синтетических проектов с проверенными эталонами;
- baseline воспроизводимо запускается пять раз на проект;
- оба контура проверки работают независимо;
- технические ошибки не смешиваются с оценкой качества;
- LLM-судья возвращает валидный структурированный результат;
- спорные и novel findings выделяются для ручной проверки;
- результаты содержат качество, стабильность, стоимость и tool trace;
- каждый запуск вызывает только харнесс и не требует работоспособности parser,
  algorithm, metrics, брокера или других сервисов;
- все graph/metrics-профили читаются из заранее подготовленного локального
  bundle;
- можно сравнить baseline минимум с бюджетами 2/4/6, четырьмя toolset и тремя
  context-вариантами без полного декартова перебора;
- итоговый отчёт позволяет выбрать конфигурацию или обоснованно оставить
  baseline.

## 16. Что не входит в MVP

- распределённое выполнение benchmark;
- автоматический подбор параметров модели;
- полный перебор всех комбинаций;
- десятки моделей и провайдеров;
- сложные статистические тесты;
- постоянная база benchmark-результатов;
- web-интерфейс;
- автоматическое изменение production-конфигурации;
- полностью автоматическое принятие novel findings без человеческой проверки.
- тестирование parser, algorithm и metrics либо проверка качества построенных
  ими артефактов;
- broker topology, consumer delivery, idempotency и публикация межсервисных
  событий.

К этим возможностям следует возвращаться только после первого полного цикла
benchmark и подтверждения, что их стоимость оправдана.
