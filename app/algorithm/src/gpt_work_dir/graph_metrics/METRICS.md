# Математические метрики графа проекта

## 1. Назначение документа

Этот документ описывает метрики, которые фактически вычисляются подсистемой
`graph_metrics`, их математический смысл, особенности реализации и ограничения.
Также здесь собраны метрики из теории графов, теории информации, статистики и
анализа программ, которые могут быть полезны PiaPav — статическому анализатору и
визуализатору архитектуры Python-проектов.

Документ разделяет три разных понятия:

- **факт** — данные, непосредственно извлечённые парсером из AST;
- **реализованная метрика** — показатель, который уже рассчитывается проектом;
- **предлагаемая метрика** — идея для развития, которой в текущем коде нет.

Это важно: число вызовов, центральность или высокий риск не доказывают наличие
дефекта. Они помогают ранжировать объекты для архитектурного ревью.

## 2. Какие графы строит проект

### 2.1. Граф зависимостей файлов

Это простой ориентированный граф

\[
G_f=(V_f,E_f),
\]

где вершина — проанализированный Python-файл, а ребро \(u\to v\) существует,
если файл `u` содержит хотя бы один импорт локального файла `v`.

Особенности текущей реализации:

- учитываются только импорты с `from_lib == false`;
- несколько импортов между одной парой файлов превращаются в одно ребро;
- петли `u → u` исключаются;
- внешние библиотеки в граф вершин не входят;
- направление означает «зависит от», то есть импортирующий файл указывает на
  импортируемый;
- граф является статическим: динамические импорты и зависимости, создаваемые
  фреймворком, могут отсутствовать.

### 2.2. Граф зависимостей пакетов

Файлы агрегируются по первому каталогу относительно корня анализа. Файлы в
корне образуют пакет `<root>`. Ребро пакетов существует, если имеется хотя бы
одно межпакетное ребро файлов. Повторы также удаляются.

Такое определение пакета удобно и детерминировано, но не обязательно совпадает с
Python package: глубоко вложенные подсистемы объединяются по первому сегменту.

### 2.3. Граф вызовов

Это ориентированный граф

\[
G_c=(V_c,E_c),
\]

где вершинами служат функции, методы, синтетические неявные конструкторы и код
уровня модуля, а ребро \(u\to v\) означает статически разрешённый локальный
вызов `v` из `u`.

Уникальное ребро и место вызова — разные сущности. Если `u` трижды вызывает
`v`, в графе одно ребро с весом, равным трём callsite. Вложенные выражения вида
`a(b(c()))` учитываются рекурсивно.

Разрешение целей основано на локальных символах, импортах, `self.method`,
суффиксах квалифицированных имён и известных внешних корнях. Динамическая
диспетчеризация, monkey patching, декораторы, DI-контейнеры и framework hooks
могут делать статический граф неполным.

## 3. Реализованные метрики

### 3.1. Размер проекта (`size`)

Это счётчики, а не оценки качества:

| Поле | Что считается |
|---|---|
| `directories` | Уникальные непустые префиксы путей каталогов; корень не считается |
| `files` | Python-файлы в результате парсера |
| `classes` | Все классы независимо от вида |
| `abstract_classes` | Классы, классифицированные как `abstract` |
| `dataclasses` | Классы, классифицированные как `dataclass` |
| `functions` | Функции уровня модуля |
| `methods` | Методы классов |
| `fields` | Поля классов, включая найденные присваивания `self.<field>` |
| `constants` | Простые константы уровня модуля |

Счётчики полезны как база для нормализации и сравнения версий одного проекта.
Сами по себе большие значения не означают плохую архитектуру.

### 3.2. Активность (`activity`)

Пусть \(C\) — число всех мест вызова, включая повторы и вложенные вызовы;
\(C_{callable}\) — вызовы внутри функций и методов; \(F\) — число функций;
\(M\) — методов; \(K\) — классов; \(O\) — число владельцев вызовов, то есть
всех функций, методов и модулей, в которых есть вызовы.

| Поле | Формула |
|---|---|
| `calls` | \(C\) |
| `local_imports` | Число записей локальных импортов, не уникальных рёбер |
| `external_imports` | Число записей внешних импортов |
| `average_calls_per_callable` | \(C_{callable}/(F+M)\) |
| `average_calls_per_call_owner` | \(C/O\) |
| `average_methods_per_class` | \(M/K\) |

При нулевом знаменателе проект возвращает `0.0`. Все средние округляются до
четырёх знаков.

### 3.3. Метрики графа зависимостей (`dependency_graph`)

Обозначим \(N=|V_f|\), \(E=|E_f|\), входящую степень вершины
\(d^-(v)\), исходящую — \(d^+(v)\).

#### Число вершин и рёбер

`nodes` равно \(N\), `edges` равно \(E\). Рёбра уникальны, поэтому эти значения
не показывают интенсивность повторных импортов.

#### Плотность

Для простого ориентированного графа без петель:

\[
density=\frac{E}{N(N-1)}.
\]

При \(N<2\) значение равно нулю. Большая плотность означает, что значительная
доля потенциальных зависимостей реализована, но сравнивать плотность проектов
разного масштаба следует осторожно: у крупных разреженных графов она естественно
снижается.

#### Fan-in и fan-out

\[
\overline{fan\_in}=\frac{1}{N}\sum_v d^-(v)=\frac{E}{N},
\qquad
\overline{fan\_out}=\frac{1}{N}\sum_v d^+(v)=\frac{E}{N}.
\]

Поэтому оба средних в любом ориентированном графе равны. Их отдельный вывод
удобен семантически, но не несёт двух независимых сигналов. Более содержательны
`highest_fan_in` и `highest_fan_out`, где возвращаются максимальная степень и
все файлы, достигшие максимума.

Высокий fan-in указывает на широко используемый файл и большой потенциальный
радиус воздействия его изменений. Высокий fan-out указывает на координатор или
объект с большим числом прямых зависимостей.

#### Компоненты связности и изоляция

- `weakly_connected_components` — число компонент после замены направленных
  рёбер неориентированными;
- `isolated_files` — вершины, у которых \(d^-=d^+=0\);
- `cyclic_components` — сильно связные компоненты размера больше одного.

Сильно связная компонента размера больше одного означает, что каждый её файл
достижим из каждого другого и, следовательно, содержит цикл зависимостей.
Самопетли здесь невозможны, так как файловые зависимости на себя исключаются.

### 3.4. Пакетная архитектура (`architecture`)

Для каждого пакета рассчитываются:

- \(C_a\), afferent coupling — число **других пакетов**, зависящих от него;
- \(C_e\), efferent coupling — число других пакетов, от которых он зависит;
- \(N_a\) — число абстрактных классов;
- \(N_c\) — общее число классов.

В той же записи `files`, `classes` и `abstract_classes` сохраняют абсолютные
размеры пакета, чтобы долевые показатели не интерпретировались без масштаба.

#### Нестабильность Роберта Мартина

\[
I=\frac{C_e}{C_a+C_e}.
\]

`I = 0` соответствует пакету без исходящих межпакетных зависимостей, `I = 1` —
пакету, от которого никто не зависит, но который сам зависит от других. Для
изолированного пакета при \(C_a+C_e=0\) реализация возвращает `0.0`; это
техническая договорённость, а не доказательство архитектурной стабильности.

#### Абстрактность

\[
A=\frac{N_a}{N_c}.
\]

Если классов нет, возвращается `0.0`. В числитель входят только классы с типом
`abstract`; Protocol и иные формы абстракции учитываются лишь в той мере, в
какой парсер классифицирует их как `abstract`.

#### Расстояние от главной последовательности

\[
D=|A+I-1|.
\]

Чем ближе `D` к нулю, тем ближе сочетание стабильности и абстрактности к главной
последовательности. Высокое `D` — сигнал для проверки, а не дефект: стабильный
пакет конкретных DTO закономерно может иметь `A = 0`, `I = 0`, `D = 1`.

#### Циклы и критическая топология

- `package_edges` — число уникальных межпакетных рёбер;
- `cyclic_package_components` — сильно связные компоненты пакетов размера
  больше одного;
- `articulation_files` — точки сочленения неориентированной проекции файлового
  графа: удаление такой вершины увеличивает число компонент;
- `bridge_dependencies` — мосты той же неориентированной проекции: удаление
  ребра увеличивает число компонент.

Точки сочленения и мосты показывают структурные «узкие места» связности, но
игнорируют направление импорта. Они не равны критическим runtime-компонентам и
не учитывают резервные пути, создаваемые динамически.

### 3.5. Метрики функций и методов (`code_quality`)

Исходные значения вычисляются отдельным AST-обходом для каждой функции и
метода. Тела вложенных функций, классов и lambda не включаются в метрику
внешнего callable.

#### Цикломатическая сложность

Начальное значение равно единице. Оно увеличивается на:

- `if`, `for`, `async for`, `while`, тернарный `if` — по 1;
- каждый `except` — по 1;
- `and`/`or` — на число дополнительных операндов;
- comprehension — на 1 плюс число его `if`;
- `match` — на `max(1, число case − 1)`.

Сам `try` увеличивает вложенность и когнитивную сложность, но не
цикломатическую. Таким образом, это конкретная AST-аппроксимация McCabe, а не
полный граф потока управления.

`average_cyclomatic_complexity` — среднее по callable. В
`high_complexity_callables` попадают элементы со значением не меньше 10 либо с
когнитивной сложностью не меньше 15.

#### Когнитивная сложность

Для управляющей конструкции добавляется \(1+L\), где \(L\) — текущая глубина
управляющей вложенности. Булевы операции добавляют число дополнительных
операндов без штрафа вложенности; comprehension добавляет число решений и
текущую глубину. Эта метрика отражает реализацию проекта и не должна считаться
побитово совместимой с одноимёнными метриками внешних анализаторов.

#### Размер и вложенность

- `lines_of_code` = `end_lineno - lineno + 1`; это физический диапазон AST-узла,
  включая сигнатуру и пустые/комментарные строки внутри диапазона, но обычно без
  строк декораторов;
- `statement_count` — число AST-узлов, являющихся `ast.stmt`;
- `max_nesting` — максимум вложенности учитываемых управляющих конструкций;
- `return_count`, `raise_count`, `await_count` — числа соответствующих AST-узлов.

Агрегированный отчёт содержит средний LOC, максимальную вложенность, десять
самых длинных callable и список элементов с вложенностью не меньше четырёх.
Некоторые исходные счётчики остаются в графе каждого callable, но отдельно не
агрегируются.

#### Async и исключения

- `async.functions` — число `async def`;
- `async.without_await` — async-функции без `await` в собственном теле;
- `raise_statements` — общее число `raise`;
- `callables_raising` — число callable хотя бы с одним `raise`;
- `raised_types` и `caught_types` — частоты статически извлечённых выражений;
- `broad_handlers` — обработчики `Exception`, `BaseException` и `bare except`.

Динамическое `raise e` записывает имя выражения, а повторный `raise` без
выражения не добавляет тип. Широкий обработчик может быть намеренным на границе
процесса, поэтому метрика требует контекста.

### 3.6. Объектно-ориентированные метрики (`object_oriented`)

Реализовано семейство Chidamber–Kemerer в адаптации к доступному статическому
графу. В отчёт выводятся рейтинги до десяти классов, причём каждая строка
содержит все шесть показателей.

`classes_analyzed` показывает число обработанных классов. Поля
`highest_weighted_method_complexity`, `highest_class_coupling`,
`largest_response_sets`, `lowest_cohesion`, `deepest_inheritance` и
`most_direct_children` — разные сортировки одного набора классов по WMC, CBO,
RFC, LCOM, DIT и NOC соответственно. Несмотря на имя `lowest_cohesion`, список
сортируется по убыванию LCOM: больший недостаток связности означает меньшую
связность класса.

#### WMC — Weighted Methods per Class

\[
WMC(C)=\sum_{m\in methods(C)} CC(m),
\]

где \(CC\) — реализованная цикломатическая сложность. Высокое значение может
возникать из-за большого числа простых методов или нескольких сложных методов.

#### CBO — Coupling Between Objects

`CBO` — число уникальных локальных классов, найденных среди:

- локальных родителей класса;
- типов его полей;
- первых сегментов имён вызываемых объектов.

Сам класс исключается. Неоднозначные короткие имена и неразрешённые ссылки не
учитываются, поэтому значение является нижней статической оценкой зацепления.

#### RFC — Response For a Class

\[
RFC(C)=|methods(C)|+|unique\ call\ names(C)|.
\]

Учитываются уникальные синтаксические имена непосредственных вызовов методов
класса, включая вложенные вызовы. Это не транзитивное замыкание и не только
локально разрешённые цели; внешние и builtin-вызовы также могут войти в набор.

#### LCOM — Lack of Cohesion of Methods

Для каждой пары методов берутся множества обнаруженных полей `self`, которые
они используют. Текущая версия рассчитывается как

\[
LCOM(C)=\frac{\#\{(m_i,m_j):F_i\cap F_j=\varnothing\}}
               {\binom{|M|}{2}}.
\]

`0` означает общие поля у каждой пары, `1` — отсутствие общих полей у всех пар.
Если пар методов нет или у класса не обнаружено ни одного поля, возвращается
`null`. Пустой набор обращений конкретного метода делает его несвязным со всеми
остальными, если в классе в целом поля существуют.

#### DIT и NOC

- `DIT` — максимальная глубина цепочки разрешённого локального наследования;
- `NOC` — число непосредственных локальных потомков.

Внешние базовые классы и неоднозначные имена не увеличивают `DIT`. Защита от
циклов наследования останавливает рекурсию, но цикл сам по себе отдельной
метрикой классов не выводится.

### 3.7. Метрики графа вызовов (`call_graph`)

#### Покрытие разрешения

Пусть \(L\) — число локально разрешённых callsite, \(X\) — известных внешних
или builtin-callsite, \(U\) — неразрешённых.

\[
local\_resolution\_rate=\frac{L}{L+X+U},
\]

\[
classified\_callsite\_rate=\frac{L+X}{L+X+U}.
\]

Эти показатели являются метриками достоверности самого статического графа.
Центральности и рейтинги особенно важно интерпретировать вместе с ними.

`callsites_in_local_edges` равно \(L\), а `edges` — числу уникальных пар
caller/target. `external_or_builtin_callsites` равно \(X\),
`unresolved_callsites` — \(U\), а `unresolved_or_external_callsites` — их сумма,
сохранённая для обратной совместимости. `heaviest_edges` ранжирует пары по числу
мест вызова.

#### Степени, роли и достижимость

- `entrypoints`: \(d^-=0, d^+>0\);
- `leaf_callables`: \(d^->0, d^+=0\);
- `isolated_callables`: \(d^-=d^+=0\);
- `highest_fan_in`, `highest_fan_out`: максимальные уникальные степени;
- `maximum_transitive_reach`: максимальный размер множества вершин, достижимых
  из одной вершины.

Это структурные роли, а не доказанные публичные точки входа, конечные операции
или мёртвый код.

`node_kinds` показывает, сколько в графе функций, методов, модульных узлов и
синтетических неявных конструкторов. Он помогает проверить состав графа перед
сравнением производных метрик.

#### Рекурсия и глубина цепочки

`recursive_components` содержит сильно связные компоненты размера больше одного
и одиночные вершины с петлёй. Для поиска самой длинной цепочки каждая такая
компонента сжимается в одну вершину; полученный граф конденсации ацикличен.

`maximum_call_chain_depth` — число рёбер одной из самых длинных цепочек графа
конденсации. Внутреннее число шагов в рекурсивной компоненте не учитывается.
`maximum_syntactic_call_nesting` измеряет совсем другое: глубину выражения
`a(b(c()))` внутри одного AST.

#### PageRank

Используется демпфирование \(d=0.85\), равномерный начальный ранг и
перераспределение веса висячих вершин между всеми вершинами:

\[
PR(v)=\frac{1-d}{N}+d\left(
\sum_{u\to v}\frac{PR(u)}{d^+(u)}+
\frac{\sum_{d^+(z)=0}PR(z)}{N}
\right).
\]

Итерации прекращаются после 100 шагов или при максимальном изменении меньше
\(10^{-10}\). `pagerank_top` содержит пять вершин. Высокий PageRank означает,
что вершину вызывают другие значимые вершины.

#### Betweenness centrality

Для направленного невзвешенного графа применяется центральность посредничества:

\[
C_B(v)=\sum_{s\ne v\ne t}\frac{\sigma_{st}(v)}{\sigma_{st}},
\]

где \(\sigma_{st}\) — число кратчайших путей из \(s\) в \(t\), а
\(\sigma_{st}(v)\) — число таких путей через \(v\). Результат нормализуется на
\((N-1)(N-2)\). `betweenness_top` содержит пять вершин. Высокое значение
указывает на посредника между подсистемами, но не обязательно на часто
исполняемый код.

#### Составной рейтинг риска

Для каждой вершины рассчитывается сырая сложность

\[
Q(v)=\max(0,CC(v)-1)+Cog(v).
\]

Затем \(Q\), fan-in, betweenness и транзитивная достижимость независимо делятся
на максимум соответствующего показателя внутри текущего проекта:

\[
Risk(v)=100(0.35\hat Q+0.25\widehat{fan\_in}
                 +0.20\widehat{betweenness}+0.20\widehat{reach}).
\]

`risk_top` содержит десять вершин с ненулевым результатом. Это относительный
эвристический рейтинг для приоритизации ревью и тестов. Его нельзя сравнивать
между проектами как абсолютную вероятность отказа; веса не обучены на истории
дефектов и не учитывают runtime-частоту, покрытие тестами или churn.

## 4. Общие ограничения реализованных метрик

1. Анализ статический и Python-специфичный. Рефлексия, динамические импорты,
   метапрограммирование и конфигурация фреймворков могут отсутствовать.
2. Качество графа вызовов зависит от разрешения символов. Неразрешённые связи
   систематически занижают степени, достижимость и центральности.
3. Граф импортов невзвешенный. Один импорт и множество импортируемых объектов
   между парой файлов дают одинаковое ребро.
4. Большинство результатов описывает снимок, а не изменение во времени.
5. Среднее скрывает неоднородность распределения; его следует читать вместе с
   максимумами, квантилями и списками лидеров.
6. Топологическая критичность не равна эксплуатационной критичности: для неё
   нужны трассировки, частоты вызовов, ошибки и требования к доступности.
7. Пороги `10`, `15` и `4`, а также веса риска являются эвристиками.
8. Округление до четырёх или шести знаков подходит для отчёта, но для сравнения
   очень близких версий желательно сохранять неокруглённые внутренние значения.

## 5. Полезные дополнительные метрики

Ниже перечислены **не реализованные сейчас** показатели. Они ранжированы по
практической ценности для архитектурного визуализатора, а не по теоретической
известности.

### 5.1. Приоритет A: можно вычислить из текущего графа

#### A1. Транзитивный радиус изменения файлов и пакетов

Для файла \(v\) полезны две величины:

\[
downstream(v)=|\{u:v\leadsto u\}|,
\qquad
impact(v)=|\{u:u\leadsto v\}|.
\]

Первая показывает число зависимостей, достижимых из файла; вторая — сколько
файлов потенциально затронет его изменение. В графе импортов направление идёт
от зависимого к зависимости, поэтому именно обратная достижимость соответствует
blast radius. Метрика дополняет прямой fan-in и особенно полезна для выбора
регрессионных тестов.

#### A2. Тяжесть циклических компонент

Одного списка SCC недостаточно. Для каждой циклической компоненты стоит вывести:

- число вершин \(|S|\) и внутренних рёбер \(|E_S|\);
- внутреннюю плотность \(|E_S|/(|S|(|S|-1))\);
- число входящих и исходящих рёбер компоненты;
- долю файлов проекта, находящихся в циклах;
- длину кратчайшего найденного цикла;
- приблизительный feedback edge set — небольшой набор рёбер, удаление которых
  сделало бы компоненту ацикличной.

Это превращает бинарный сигнал «цикл есть» в приоритетный список рефакторинга.

#### A3. Центральности графа импортов

PageRank и betweenness уже считаются для вызовов, но не для файлов. Для
архитектурной карты полезны:

- **PageRank** — фундаментальные файлы, на которые указывают значимые файлы;
- **betweenness** — архитектурные посредники между областями;
- **harmonic centrality**
  \(H(v)=\sum_{u\ne v,\ d(u,v)<\infty}1/d(u,v)\), пригодная для несвязных
  графов лучше обычной closeness;
- **HITS**: authority для общих зависимостей и hub для координаторов.

Центральности нужно сопровождать направлением графа и не смешивать с частотой
runtime-исполнения.

#### A4. Связность внутри пакета и между пакетами

Для пакета \(P\):

\[
cohesion(P)=\frac{|E_{P\to P}|}{|P|(|P|-1)},
\]

а для проекта:

\[
cross\_package\_ratio=\frac{|E_{cross}|}{|E_f|}.
\]

Дополнительно полезны conductance и cut ratio границы пакета. Они отвечают на
вопрос, соответствует ли файловая структура фактическим зависимостям. Низкая
внутренняя связность при большом числе внешних рёбер может указывать на
искусственную группировку.

#### A5. Распределения вместо одних средних

Для fan-in, fan-out, LOC, сложности, WMC, CBO и RFC стоит выводить медиану,
квантили `p75`, `p90`, `p95`, максимум и MAD/IQR. Это устойчивее среднего при
наличии нескольких «богатых» узлов и позволяет сравнивать проекты разного
размера.

#### A6. Концентрация зависимостей

По нормированным входящим степеням \(p_i=d^-(i)/E\) можно считать:

- энтропию Шеннона \(H=-\sum p_i\log p_i\);
- нормированную энтропию \(H/\log N\);
- индекс Херфиндаля–Хиршмана \(HHI=\sum p_i^2\);
- коэффициент Джини распределения степеней.

Высокая концентрация означает, что зависимости сходятся к небольшому ядру.
Это может быть хорошей платформенной архитектурой или опасным «god module»;
графическая карта поможет различить случаи.

#### A7. k-core / coreness

`k-core` — максимальный подграф, где степень каждой вершины не меньше `k`
(обычно на неориентированной проекции). Coreness выделяет плотное архитектурное
ядро и менее чувствителен к одиночной звезде, чем простая степень. Полезно
показывать ядро отдельным визуальным слоем.

#### A8. Reciprocity и assortativity

- reciprocity — доля направленных рёбер, для которых существует обратное;
- degree assortativity — склонность вершин связываться с вершинами похожей
  степени.

Высокая reciprocity в графе импортов является дешёвым индикатором взаимных
зависимостей. Assortativity помогает отличить иерархию «много листьев → ядро»
от сети плотно связанных крупных модулей, но на малых графах нестабильна.

#### A9. Модулярность и сообщества

Алгоритмы Louvain/Leiden или спектральная кластеризация на неориентированной
взвешенной проекции могут находить сообщества. Модулярность

\[
Q=\frac{1}{2m}\sum_{ij}\left(A_{ij}-\frac{k_i k_j}{2m}\right)
\mathbf{1}[c_i=c_j]
\]

показывает, насколько связи концентрируются внутри найденных групп. Сравнение
сообществ с каталогами выявляет расхождение логической и файловой архитектуры.
Результат зависит от алгоритма, resolution parameter и случайного seed, поэтому
их нужно фиксировать.

#### A10. Избыточность и устойчивость путей

Полезны локальная vertex/edge connectivity и число независимых путей между
важными вершинами. В отличие от точек сочленения и мостов, эти показатели
оценивают степень резервирования связей. Для больших графов полный расчёт дорог,
поэтому его разумно ограничить ключевыми вершинами или пакетами.

### 5.2. Приоритет B: требуют небольшого расширения AST-данных

#### B1. Взвешенный граф зависимостей

Вес ребра может учитывать число импортируемых символов, число обращений к ним
или разные типы связи: import, call, inheritance, annotation. Следует хранить
вектор весов по типам, а не сразу сворачивать всё в одно число. Тогда доступны
взвешенные степени, PageRank, shortest path и межпакетное зацепление.

#### B2. TCC и LCC для классов

Tight Class Cohesion и Loose Class Cohesion оценивают долю пар методов,
соединённых общим полем напрямую или транзитивно. Они лучше дополняют текущий
LCOM для классов с группами методов. Желательно отдельно учитывать properties,
class/static methods и обращения через вспомогательные методы.

#### B3. LCOM4

Строится двудольный граф «методы–поля» плюс связи вызовов методов; число его
компонент показывает число независимых обязанностей класса. Значение больше
одного является понятным кандидатом на разделение класса. Нужны надёжные связи
`self.method()` и более точное различение полей.

#### B4. Halstead и Maintainability Index

Из токенов операторов и операндов можно получить словари \(n_1,n_2\), длины
\(N_1,N_2\), объём

\[
V=(N_1+N_2)\log_2(n_1+n_2)
\]

и производные Halstead. Maintainability Index объединяет Halstead volume,
цикломатическую сложность и LOC. Эти показатели известны, но чувствительны к
варианту формулы и стилю языка; в отчёте необходимо фиксировать точное
определение, а не показывать безымянный `MI`.

#### B5. NPath complexity

NPath приближает число ациклических путей выполнения и быстрее растёт при
последовательных независимых ветвлениях, чем McCabe. Она хорошо выявляет
функции, для которых полный набор комбинаций тестов становится непрактичным.
Для Python нужно явно определить правила для `match`, comprehensions,
`try/except/else/finally` и короткого замыкания.

#### B6. Метрики API и сигнатур

Полезны число публичных символов, доля аннотированных аргументов и return type,
ширина сигнатуры, доля optional/default аргументов, документированность и
отношение публичного API к внутренней реализации. Для корректности необходимо
определить соглашения публичности (`_name`, `__all__`, framework routes).

#### B7. Instability на уровне файлов и классов

Формулу Мартина можно применять к любому уровню графа:

\[
I(v)=\frac{d^+(v)}{d^-(v)+d^+(v)}.
\]

Технически степени уже доступны, но интерпретация станет сильнее после
разделения видов связей. Изолированной вершине лучше отдавать `null`, а не
создавать впечатление максимальной стабильности.

#### B8. Dominators графа вызовов

В ориентированном графе с известной точкой входа вершина `d` доминирует `v`,
если каждый путь от входа к `v` проходит через `d`. Доминирующие callable —
естественные места для наблюдаемости, авторизации и fault isolation. Для этой
метрики нужны достоверные entrypoint и, вероятно, отдельный супер-корень.

### 5.3. Приоритет C: требуют внешних или исторических данных

#### C1. Change coupling

По истории изменений строится взвешенный граф совместно меняющихся файлов:

\[
coupling(a,b)=\frac{commits(a,b)}{\min(commits(a),commits(b))}.
\]

Сильная совместная изменяемость без статической связи выявляет скрытую
архитектурную зависимость. Нужна история системы контроля версий; текущий AST
её не содержит.

#### C2. Churn × complexity

Произведение нормализованного churn и сложности выделяет сложный и часто
изменяемый код — обычно более сильный приоритет ревью, чем каждая метрика по
отдельности. Нужны история изменений и выбранное временное окно.

#### C3. Покрытие и мутационный балл

Сочетание центральности, сложности и test coverage помогает находить важный,
но плохо проверенный код. Mutation score лучше обычного покрытия оценивает силу
тестов. Эти данные должны приходить из инструмента тестирования, а не выводиться
из статической структуры.

#### C4. Runtime-веса

Трассировки позволяют взвесить рёбра числом вызовов, временем, ошибками и
latency. Тогда betweenness и critical path отражают реальную нагрузку. Следует
хранить статический и runtime-графы раздельно: редко исполняемый аварийный путь
может быть критичен, даже если имеет малый вес.

#### C5. Метрики дефектов

Defect density, escaped defects и mean time to repair дают возможность проверить,
действительно ли `risk_top` предсказывает проблемные области. После накопления
данных веса составного риска можно калибровать, обязательно сохраняя объяснимые
компоненты результата.

## 6. Рекомендуемый порядок развития

Наиболее полезная последовательность для PiaPav:

1. Добавить транзитивный `impact` файлов/пакетов и показатели тяжести SCC.
   Данные уже есть, а результат непосредственно полезен для визуализации.
2. Добавить к распределениям медиану, `p90`, `p95` и IQR; это устранит слабость
   отчёта, основанного преимущественно на средних и максимумах.
3. Рассчитать PageRank, betweenness и harmonic centrality для графа импортов,
   переиспользовав смысл уже знакомых пользователю метрик графа вызовов.
4. Добавить внутрипакетную cohesion, долю межпакетных рёбер и сопоставление
   каталогов с найденными сообществами.
5. Улучшить confidence-метрики: отдельно показать долю разрешённых локальных
   импортов, вызовов и типов; при низкой полноте помечать производные рейтинги.
6. Только затем вводить дополнительные составные рейтинги. Каждый рейтинг
   должен сохранять исходные компоненты, формулу, версию и область нормализации.
7. После появления истории изменений и покрытия объединить структуру с churn и
   тестовыми данными; это даст более практичный прогноз риска, чем дальнейшее
   усложнение чисто топологических формул.

## 7. Правила корректного сравнения

- Сравнивать версии нужно на одинаковом корне анализа и одинаковой версии
  парсера.
- Абсолютные счётчики следует нормализовать по числу файлов, callable или LOC.
- Для межпроектного сравнения предпочтительны квантили и доли, но различия
  домена и архитектурного стиля всё равно должны учитываться.
- Изменение метрики значимо только вместе с изменившимися вершинами и рёбрами;
  одна итоговая цифра не объясняет причину.
- Центральности разных размеров графа нельзя напрямую сравнивать без одинаковой
  нормализации.
- Составной риск должен версионироваться при изменении формулы или весов.
- `null` следует использовать для неприменимой метрики, `0` — только для
  применимой метрики с нулевым результатом.
- Любой архитектурный порог лучше калибровать на истории самого проекта, а не
  считать универсальным законом.

## 8. Итог

Текущая подсистема уже покрывает четыре важных уровня: локальную сложность
callable, объектные свойства классов, топологию импортов и топологию вызовов.
Её сильная сторона — объяснимые результаты, связанные с конкретными файлами и
символами. Главные зоны роста — измерение транзитивного радиуса изменений,
тяжести циклов, качества модульных границ и статистических распределений, а
затем объединение статической архитектуры с историей изменений, тестами и
runtime-наблюдениями.
