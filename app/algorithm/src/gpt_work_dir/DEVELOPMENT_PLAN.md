# План развития ядра архитектурного анализатора

## 1. Цель

`gpt_work_dir` должен стать ядром статического анализатора Python-проектов,
которое преобразует исходный код в связный архитектурный граф.

- **Узлы графа** — пакеты, модули, классы, функции, методы и другие структуры.
- **Рёбра графа** — импорты, вызовы, наследование, создание объектов,
  использование типов и владение структурами.
- **Атрибуты** — координаты в исходном коде, сигнатуры, метрики, способ и
  уверенность разрешения связи.

Анализатор должен позволять определить:

- какие структуры существуют в проекте;
- кто кого вызывает;
- кто от кого зависит и через какой импорт;
- какие связи разрешены точно, предположительно или неоднозначно;
- какие архитектурные слои и компоненты образуются;
- где находятся циклы и точки высокой связанности;
- какие структуры будут затронуты изменением выбранного элемента.

## 2. Основные принципы

1. Не исполнять исследуемый код.
2. Отделять факты, полученные из AST, от архитектурных эвристик.
3. Не подменять неоднозначность ложной точностью.
4. Сохранять координаты каждого найденного факта в исходном коде.
5. Поддерживать детерминированный результат и стабильные идентификаторы.
6. Строить разные представления архитектуры из единого семантического графа.
7. По возможности сохранять обратную совместимость текущего JSON-контракта.

## 3. Нормализованная модель графа

Текущий вложенный JSON удобен для просмотра, но недостаточно удобен для
графовых алгоритмов. Необходимо ввести внутреннее представление `nodes + edges`,
сохранив текущий формат как одну из выходных проекций.

### 3.1. Узлы

Минимальные виды узлов:

- project;
- package;
- module;
- class;
- method;
- function;
- module-level code;
- field;
- constant;
- external module;
- unresolved symbol.

Каждый узел должен иметь стабильный квалифицированный идентификатор:

```text
module:services.orders
class:services.orders.OrderService
method:services.orders.OrderService.create
function:services.orders.validate_order
```

Минимальные атрибуты узла:

- `id`;
- `kind`;
- `qualified_name`;
- `display_name`;
- `location`;
- `parent_id`;
- `attributes` с данными конкретного вида структуры.

### 3.2. Рёбра

Основные типы рёбер:

- `contains`;
- `imports_module`;
- `imports_symbol`;
- `calls`;
- `awaits`;
- `inherits`;
- `implements`;
- `overrides`;
- `instantiates`;
- `uses_type`;
- `reads`;
- `writes`;
- `decorated_by`;
- `registers_callback`;
- `raises`;
- `handles`;
- `reexports`.

Каждое ребро должно содержать источник, цель, вид связи, все места её появления
и качество разрешения:

```json
{
  "source": "method:app.service.OrderService.create",
  "target": "method:app.repository.OrderRepository.save",
  "kind": "calls",
  "locations": [
    {
      "file": "app/service.py",
      "line": 31,
      "column": 8
    }
  ],
  "resolution": "exact",
  "confidence": 1.0
}
```

Допустимые состояния разрешения:

- `exact`;
- `probable`;
- `ambiguous`;
- `external`;
- `unresolved`;
- `dynamic`.

Для неоднозначной связи необходимо сохранять список кандидатов, а не выбирать
первое совпадение.

### 3.3. Представления результата

Следует разделить:

1. внутреннюю нормализованную модель;
2. публичный семантический граф;
3. совместимое вложенное представление;
4. проекции для визуализации;
5. компактные представления для LLM.

## 4. Таблица символов и разрешение имён

Это приоритетное направление развития. Для каждого scope необходимо собирать:

- параметры;
- локальные переменные;
- функции и классы;
- импортированные символы и aliases;
- поля экземпляра и класса;
- `global` и `nonlocal`;
- результаты присваиваний;
- символы окружающих scopes.

Разрешение имени должно выполняться по явной цепочке:

```text
local → enclosing → module → imported → builtins → unresolved
```

Нужно поддержать:

- qualified names;
- одинаковые короткие имена в разных модулях;
- вложенные функции и классы;
- замыкания;
- aliases;
- условные определения;
- несколько возможных источников значения.

## 5. Распространение типов

Для повышения точности графа вызовов требуется ограниченный статический data
flow без попытки превратить проект в полноценный type checker.

Источники информации о типах:

- вызов конструктора;
- аннотация переменной;
- аннотация параметра;
- аннотация возвращаемого значения;
- присваивание;
- поля dataclass;
- присваивания `self.field` в `__init__`;
- `typing.cast`;
- сужение через `isinstance`;
- простые generic-контейнеры.

Приоритетные случаи:

```python
service = OrderService()
service.create()
```

```python
service: OrderService
service.create()
```

```python
def get_service() -> OrderService:
    ...

service = get_service()
service.create()
```

```python
self.repository = SqlRepository()
self.repository.save()
```

При слиянии веток нужно сохранять объединение возможных типов и помечать
результат как неоднозначный, если единственная цель не доказана.

## 6. Развитие графа вызовов

### 6.1. Базовые конструкции

- вызовы функций и методов;
- вызовы через `self` и `cls`;
- конструкторы;
- статические и классовые методы;
- цепочки атрибутов;
- вложенные и повторные вызовы;
- вызовы на уровне модуля.

### 6.2. Наследование и полиморфизм

- разрешение `super()` с учётом MRO;
- связь `overrides` между методами;
- набор возможных целей полиморфного вызова;
- различение точной и потенциальной цели.

### 6.3. Функции как значения

Поддержать простые случаи передачи ссылок на функции:

```python
handler = process_order
handler(order)
```

```python
map(transform, values)
```

### 6.4. Callback и декораторы

Выделять архитектурно значимые связи:

```python
router.add_route("/orders", create_order)
signal.connect(on_created)
```

```python
@router.get("/users")
def get_users():
    ...
```

Декоратор должен создавать `decorated_by`, а регистрация обработчика —
`registers_callback`. Производное ребро выполнения следует создавать только при
достаточной уверенности.

### 6.5. Асинхронное исполнение

Различать:

- обычный `calls`;
- `awaits`;
- постановку задачи через `create_task`;
- callback;
- передачу управления через `yield from`.

### 6.6. Динамические вызовы

Неразрешимые статически конструкции не должны исчезать из графа:

```python
getattr(service, method_name)()
container.resolve(Service).run()
```

Для них нужно создавать dynamic/unresolved-узлы и сохранять выражение,
координаты и возможных кандидатов.

## 7. Развитие импортного графа

Необходимо поддерживать и различать:

- `import package.module`;
- `from package import symbol`;
- aliases;
- относительные импорты любой глубины;
- `__init__.py` и namespace packages;
- re-export;
- `__all__`;
- star-import;
- импорты внутри функций;
- условные импорты;
- optional imports через `try/except ImportError`;
- импорты под `TYPE_CHECKING`;
- внешние зависимости.

Граф должен отдельно представлять:

- зависимость модуля от модуля;
- импорт конкретного символа;
- runtime dependency;
- type-only dependency;
- optional dependency;
- re-exported dependency.

## 8. Отношения между классами

Для анализа объектной архитектуры необходимо строить:

- `inherits` — наследование;
- `implements` — реализация ABC или Protocol;
- `overrides` — переопределение метода;
- `instantiates` — создание экземпляра;
- `uses_type` — использование типа в аннотациях;
- `has_dependency` или эквивалентную производную связь композиции.

Пример композиции:

```python
class Service:
    def __init__(self, repository: Repository):
        self.repository = repository
```

Связь `Service → Repository` должна выводиться из параметра и присваивания поля,
а не только из факта импорта.

Поддерживаемые источники интерфейсных отношений:

- `abc.ABC` и abstract methods;
- `typing.Protocol`;
- явное наследование;
- структурное совпадение только как вероятная связь.

## 9. Факты и архитектурные выводы

Слой извлечения должен сохранять только проверяемые факты:

- объявление структуры;
- импорт;
- вызов в конкретной позиции;
- наследование;
- аннотацию;
- присваивание;
- создание объекта.

Отдельный слой должен выводить:

- архитектурные компоненты;
- слои приложения;
- entry points;
- controllers, services и repositories;
- циклические зависимости;
- точки высокой связанности;
- нарушения границ компонентов;
- blast radius изменения;
- критические структуры.

Целевая схема обработки:

```text
Исходные файлы
    ↓
AST-факты
    ↓
Таблицы символов и разрешение типов
    ↓
Нормализованный семантический граф
    ↓
Архитектурные проекции
    ↓
Метрики / визуализация / LLM
```

## 10. Уровни архитектурного графа

Из единого семантического графа должны строиться следующие проекции.

### 10.1. Граф модулей

Узлы — модули, рёбра — imports и агрегированные вызовы. Используется для поиска
циклов, слоёв и нарушения направлений зависимостей.

### 10.2. Граф классов

Узлы — классы, рёбра — наследование, композиция, создание объектов, типы и
агрегированные вызовы методов.

### 10.3. Граф функций и методов

Максимально подробный call graph с call sites, уверенностью и возможными целями.

### 10.4. Граф пакетов

Агрегированное представление для крупных проектов.

### 10.5. Граф компонентов

Группировка может определяться:

- структурой директорий;
- Python-пакетами;
- пользовательской конфигурацией;
- автоматически найденными сообществами графа.

Агрегированное ребро должно сохранять ссылки на исходные низкоуровневые связи.

## 11. Устойчивость анализа

### 11.1. Частичный результат

Ошибка одного файла не должна уничтожать граф всего проекта. Анализатор должен
возвращать доступный результат и диагностику:

```json
{
  "graph": {},
  "diagnostics": [
    {
      "file": "broken.py",
      "severity": "error",
      "kind": "syntax_error",
      "message": "...",
      "line": 14
    }
  ]
}
```

### 11.2. Диагностика

Необходимо фиксировать:

- ошибки чтения и синтаксиса;
- неоднозначные импорты;
- неразрешённые вызовы;
- дубли идентификаторов;
- неподдерживаемые конструкции;
- несовместимую версию синтаксиса;
- внутренние нарушения контракта графа.

### 11.3. Инкрементальный анализ

В перспективе:

- хешировать содержимое файлов;
- повторно анализировать только изменившиеся модули;
- инвалидировать зависимые части графа;
- сохранять стабильные ID между запусками;
- поддерживать сравнение двух версий архитектуры.

## 12. Тестовая стратегия

### 12.1. Feature-тесты

Каждая языковая конструкция должна иметь минимальный отдельный fixture:

- alias import;
- re-export;
- относительный импорт;
- одинаковые имена структур;
- `self.field.method()`;
- распространение return type;
- inheritance и override;
- `super()`;
- ABC и Protocol;
- callback;
- decorator;
- async/await;
- `TYPE_CHECKING`;
- nested scopes и closures;
- conditional assignment;
- ambiguous resolution;
- dynamic call.

Тесты должны проверять конкретные узлы и рёбра. Golden graph следует оставить
для проверки общего контракта и детерминированности.

### 12.2. Корпус проектов

Нужен набор небольших реальных или репрезентативных проектов:

- обычный Python package;
- FastAPI;
- Flask;
- Django;
- CLI-приложение;
- asyncio-приложение;
- библиотека с активным использованием typing и Protocol.

### 12.3. Метрики качества анализатора

На размеченном корпусе измерять:

- precision рёбер;
- recall рёбер;
- долю `exact`;
- долю `ambiguous`;
- долю `unresolved`;
- количество ложных связей;
- время анализа на файл;
- потребление памяти;
- стабильность ID;
- детерминированность результата.

Приоритет качества — минимизация ложных связей при постепенном росте полноты.

## 13. Этапы реализации

### Этап 1. Контракт семантического графа

1. Ввести стабильные ID узлов.
2. Ввести нормализованные `nodes` и `edges`.
3. Типизировать рёбра.
4. Добавить locations, resolution и confidence.
5. Сохранить текущий JSON как совместимую проекцию.

**Результат:** единая основа для графовых алгоритмов и последующего развития.

### Этап 2. Таблица символов

1. Построить дерево scopes.
2. Создать symbol table каждого scope.
3. Учесть импорты и aliases.
4. Реализовать разрешение qualified names.
5. Ввести явное представление неоднозначности.

**Результат:** предсказуемое разрешение имён без выбора по короткому имени.

### Этап 3. Распространение типов

1. Конструкторы.
2. Аннотации параметров и переменных.
3. Return types.
4. Поля `self`.
5. Передача типов через присваивания.
6. Простое слияние веток.

**Результат:** существенный рост точности call graph.

### Этап 4. Объектная архитектура

1. Композиция и dependency injection.
2. Protocol и ABC.
3. Override.
4. `super()` и MRO.
5. Instantiation и type-use edges.

**Результат:** полноценная class-level архитектурная проекция.

### Этап 5. Расширенные конструкции Python

1. Re-exports и `__all__`.
2. `TYPE_CHECKING` и optional imports.
3. Callbacks.
4. Decorators.
5. Async execution.
6. Nested scopes.
7. Dynamic и unresolved placeholders.

### Этап 6. Архитектурные проекции

1. Module graph.
2. Package graph.
3. Class graph.
4. Call graph.
5. Component grouping.
6. Cycles и blast radius.
7. Сравнение двух версий графа.

### Этап 7. Масштабирование и качество

1. Частичные результаты и diagnostics.
2. Инкрементальный анализ.
3. Корпус benchmark-проектов.
4. Измерение precision и recall.
5. Контроль времени и памяти.

## 14. Ближайший практический приоритет

До расширения визуализатора и набора метрик рекомендуется выполнить:

1. нормализованную модель `nodes + edges`;
2. стабильные qualified IDs;
3. дерево scopes и таблицы символов;
4. распространение типов;
5. разрешение `self.field.method()`, return types, override и `super()`;
6. измерение качества разрешения на размеченном корпусе.

Именно этот набор превратит текущий извлекатель AST-структур в ядро
семантического анализа архитектуры.

## 15. Критерии готовности первой зрелой версии

- каждый узел имеет стабильный ID;
- каждое ребро имеет тип и координаты в исходном коде;
- call sites не теряются при агрегации одинаковых связей;
- неоднозначные связи не выдаются за точные;
- строятся согласованные module, package, class и call projections;
- ошибка отдельного файла не прерывает анализ остальных файлов;
- результат детерминирован;
- графы двух версий проекта можно корректно сравнить;
- на размеченном корпусе измеряются precision и recall;
- ограничения и неподдерживаемые конструкции представлены диагностикой.
