# План создания анализатора Python-проекта

## 1. Цель первой версии

Реализовать статический анализатор, который получает путь к корню Python-проекта, обходит его `.py`-файлы и возвращает словарь в формате текущего эталона `tests/project1/graph/graph.json`.

Первая версия должна извлекать:

- файлы и их модульные пути;
- импорты, импортированные имена и алиасы;
- классы, функции и методы;
- родителей классов;
- поля, аннотации и простые значения;
- признаки `dataclass`, `Enum` и абстрактного класса;
- аргументы и возвращаемые типы функций и методов;
- все места вызовов, включая одинаковые и вложенные вызовы;
- простые межфайловые связи через импорты и вызовы.

Публичная точка входа остаётся простой:

```python
def starter(input_project: str | Path) -> dict:
    ...
```

Сохранение результата в файл не смешивается с анализом. При необходимости добавляется отдельная функция `save_graph(graph, output_path)`.

## 2. Ограничения первой версии

В первую версию не входят:

- выполнение анализируемого кода;
- полная система типов Python;
- точное разрешение `getattr`, monkey patching и динамических импортов;
- анализ сторонних библиотек;
- полноценный data flow между всеми переменными;
- отдельная универсальная модель `nodes/edges`.

Если вызов нельзя разрешить надёжно, в результат записывается его синтаксическое имя. Анализатор не должен придумывать несуществующую цель.

## 3. Общая схема обработки

Анализ выполняется в несколько проходов:

1. Найти Python-файлы проекта и построить индекс `модуль -> файл`.
2. Построить `ast.Module` для каждого файла.
3. Собрать определения, импорты и локальные таблицы имён без разрешения вызовов.
4. Разрешить алиасы, типы простых переменных и цели вызовов на основе общего индекса проекта.
5. Собрать результат в текущем JSON-формате и проверить его целостность.

Разделение на проходы обязательно: вызов может ссылаться на структуру из файла, который ещё не был обработан.

## 4. Структура модулей

```text
parser/
├── __init__.py
├── logic/
│   ├── __init__.py
│   ├── main.py
│   ├── project_index.py
│   ├── models.py
│   ├── scope.py
│   ├── expressions.py
│   ├── definitions.py
│   ├── imports.py
│   ├── calls.py
│   ├── classifiers.py
│   ├── analyzer.py
│   ├── serializer.py
│   ├── validation.py
│   └── errors.py
└── visualizer/
    ├── __init__.py
    ├── __main__.py
    └── renderer.py
```

`logic` не зависит от визуализатора. Общий `parser/__init__.py` только переэкспортирует публичные функции обеих подсистем.

### `main.py`

Только публичный API и связывание компонентов. Здесь не должно быть логики обхода AST.

- `starter(input_project) -> dict`;
- проверка входного пути;
- создание `ProjectAnalyzer`;
- возврат готового словаря.

### `project_index.py`

Отвечает за файловую систему и имена модулей.

- рекурсивно находит `.py`-файлы;
- игнорирует `__pycache__`, виртуальные окружения и скрытые служебные каталоги;
- вычисляет путь относительно корня проекта;
- строит однозначный индекс модулей;
- разрешает абсолютные и относительные импорты только внутри проекта.

Индекс должен работать по точному имени модуля, а не искать совпадение только по последнему фрагменту пути: два разных пакета могут содержать одинаковый `models.py`.

### `models.py`

Содержит внутренние `dataclass`-модели фактов анализа:

- `ModuleInfo`;
- `ImportInfo`;
- `ClassInfo`;
- `FunctionInfo`;
- `FieldInfo`;
- `ArgumentInfo`;
- `CallInfo`;
- `ExpressionInfo`.

Это внутренний формат, не привязанный напрямую к JSON. Он позволяет менять извлечение и сериализацию независимо друг от друга.

Каждый факт, где это полезно для отладки, хранит `file`, `line` и `column`, даже если первая версия сериализатора пока не выводит позиции в эталонный JSON.

### `scope.py`

Управляет областями видимости во время обхода AST.

- модуль;
- класс;
- функция или метод;
- локальные имена;
- параметры;
- импортированные алиасы;
- известные типы переменных.

Состояние создаётся отдельно для каждого файла. Глобального изменяемого состояния быть не должно.

### `expressions.py`

Преобразует AST-выражения в компактный формат значений текущего графа.

Поддерживает как минимум:

- константы;
- списки, кортежи и словари;
- имена;
- атрибуты (`EnumTypes.red`, `create_data.name`);
- индексы (`xy[0]`);
- вложенные вызовы;
- унарные простые значения.

Для неподдержанного выражения используется `ast.unparse(node)`, чтобы факт не потерялся.

### `definitions.py`

Извлекает структуры из одного AST-файла.

- классы и родителей;
- функции и методы;
- `__init__` наравне с другими методами;
- параметры, значения по умолчанию и return type;
- аннотированные поля класса;
- `self.<name>` из присваиваний внутри `__init__`;
- функции уровня модуля.

Модуль только собирает факты. Он не должен самостоятельно искать файлы импортированных объектов.

### `imports.py`

Извлекает и разрешает импорты.

- `import package`;
- `import package as alias`;
- `from package import Object`;
- `from package import Object as Alias`;
- относительные импорты;
- несколько имён в одном операторе.

Для каждой записи отдельно хранятся:

- исходный модуль;
- исходное имя объекта;
- локальный алиас;
- разрешённый локальный модуль, если он найден;
- `from_lib`.

В выходном JSON алиас записывается в той же записи импорта через `asname`.

### `calls.py`

Извлекает callsite и пытается определить их цель.

- сохраняет каждый `ast.Call` отдельно;
- рекурсивно обрабатывает вложенные вызовы;
- сохраняет позиционные и именованные аргументы;
- разрешает прямой вызов импортированной функции;
- разрешает конструктор импортированного класса;
- выполняет простое распространение типа: после `sc = SomeClass()` вызов `sc.create()` связывается с `SomeClass.create`;
- сохраняет цепочки атрибутов вроде `self.data.points.append`;
- не удаляет вызовы стандартной библиотеки и методов коллекций из фактов файла.

Конструкторы во внешнем формате обозначаются единообразно: `ClassName.__init__`.

### `classifiers.py`

Содержит узкие правила для классических Python-структур.

- `@dataclass` -> `type: "dataclass"`;
- наследование от `Enum` -> `type: "enum"`;
- наследование от `ABC` или наличие абстрактных методов -> кандидат на абстрактный класс;
- конкретный потомок ABC считается обычным классом, если реализовал все известные абстрактные методы;
- остальные классы -> `type: "class"`.

Классификация выполняется после сбора всех классов, чтобы были доступны родители и их методы.

### `analyzer.py`

Оркестратор проходов анализа.

- получает `ProjectIndex`;
- парсит файлы через встроенный `ast`;
- запускает сбор определений и импортов;
- запускает разрешение классов и вызовов;
- передаёт внутренние модели сериализатору.

Используется композиция компонентов. `ProjectAnalyzer` не наследуется от набора mixin-обработчиков AST.

### `serializer.py`

Единственное место, которое знает точную структуру `graph.json`.

- сортирует файлы детерминированно по относительному пути;
- сохраняет порядок определений и вызовов из исходного файла;
- не удаляет повторные callsite;
- опускает необязательные пустые разделы так же, как эталон;
- выдаёт JSON-совместимый `dict`;
- при отдельном вызове сохраняет UTF-8 JSON с `ensure_ascii=False`.

### `validation.py`

Проверяет результат до возврата пользователю.

- уникальность файлов;
- наличие обязательных полей;
- допустимые типы классов;
- согласованность `object/asname` импорта;
- корректность списков методов, функций и вызовов;
- возможность сериализации стандартным `json.dumps`.

### `errors.py`

Небольшой набор предметных исключений:

- `ProjectNotFoundError`;
- `SourceReadError`;
- `SourceSyntaxError` с путём, строкой и колонкой;
- `GraphValidationError`.

## 5. Правила построения имён

Чтобы связи между файлами были стабильными, необходимо заранее зафиксировать правила:

- корнем анализа считается каталог, переданный в `starter`;
- имя файла — `Path.stem`;
- `path` — относительный пакет без имени файла, через точки;
- полное имя локального модуля — `path + name`;
- локальный объект разрешается как `module.Class`, `module.function` или `module.Class.method`;
- в конечном JSON можно оставлять короткие имена, как в эталоне, но внутри анализатора всегда используются полные имена;
- алиас никогда не заменяет настоящее имя объекта во внутренней модели.

Для длинных импортов тестового проекта индекс должен уметь сопоставить `gpt_work_dir.tests.project1.data.models` с локальным модулем `models` относительно выбранного корня `data`.

## 6. Очерёдность реализации

### Этап 1. Зафиксировать контракт результата

- оформить модели всех полей текущего `graph.json`;
- описать обязательные и необязательные поля;
- добавить загрузку эталонного JSON как проверку контракта;
- не менять формат во время реализации извлечения без отдельного решения.

Результат: сериализатор способен собрать валидный пустой или вручную созданный граф.

### Этап 2. Индексация проекта и базовый AST

- реализовать поиск файлов;
- вычисление модулей и относительных путей;
- чтение UTF-8 исходников;
- `ast.parse` с понятной ошибкой синтаксиса.

Результат: пять файлов `project1/data` найдены и представлены как пять `ModuleInfo`.

### Этап 3. Импорты и структуры

- реализовать `Import` и `ImportFrom`;
- реализовать классы, функции, методы и сигнатуры;
- реализовать поля и простые аннотации;
- добавить таблицы областей видимости.

Результат: структура файлов, классов и функций совпадает с эталоном без учёта вызовов.

### Этап 4. Специальные классы

- реализовать `dataclass`;
- реализовать `Enum` и его элементы;
- реализовать ABC и абстрактные методы;
- проверить, что `SomeInterface` абстрактный, а `SomeClass` конкретный.

### Этап 5. Вызовы и простое разрешение имён

- извлечь все `ast.Call`;
- сохранить вложенные аргументы;
- применить таблицу импортов и алиасов;
- добавить простое определение типа переменной после вызова конструктора;
- разрешить `SC()`, `sc.create()`, `CreateData(...)`, `get_random_x_y()`;
- сохранить `append` и оба вызова `random.randint`.

### Этап 6. Сериализация и golden test

- получить граф для `tests/project1/data`;
- сравнить его с `tests/project1/graph/graph.json`;
- выводить удобный diff при несовпадении;
- добиться полностью детерминированного результата.

### Этап 7. Набор граничных тестов

Добавить маленькие проекты или отдельные файлы для случаев:

- абсолютный и относительный импорт;
- два модуля с одинаковым именем файла;
- импорт с алиасом;
- вложенный вызов;
- два одинаковых вызова на одной строке;
- обычный класс, dataclass, Enum и ABC;
- наследование через несколько уровней;
- `staticmethod`, `classmethod`, `property`;
- `async def` и `await`;
- значение по умолчанию и keyword-only аргумент;
- синтаксическая ошибка с указанием файла и строки.

## 7. Проверка результата на `project1`

Минимальные критерии готовности:

- найдено ровно пять Python-файлов;
- `SomeClass as SC` хранится как импорт `SomeClass` с `asname: "SC"`;
- вызовы в `main.py` разрешены в `SomeClass.__init__`, `SomeClass.create` и `CreateData.__init__`;
- `SomeInterface.type == "abstract"`;
- `SomeClass.type == "class"`;
- у `SomeClass` есть `__init__`, `create` и `clear`;
- `create` содержит `get_random_x_y`, `Cell.__init__` и `self.data.points.append`;
- `clear` содержит `Data.__init__`;
- `generator.py` содержит два отдельных вызова `random.randint`;
- dataclass-поля и ссылки `Data -> Cell`, `Cell -> EnumTypes`, `CreateData -> EnumTypes` не теряются;
- повторный запуск без изменений создаёт идентичный JSON.

## 8. Принципы поддержки кода парсера

- Один модуль — одна основная ответственность.
- AST-обход не обращается к файловой системе.
- Разрешение импортов не сериализует JSON.
- Сериализатор не делает новых выводов о коде.
- Компоненты получают зависимости через конструкторы, без скрытого глобального состояния.
- Не использовать строковый разбор Python-конструкций там, где нужные данные уже есть в AST.
- Каждое исправление ошибки парсинга сначала закреплять минимальным тестом.
- Внутренние модели и функции снабжать типами, чтобы устройство самого анализатора можно было понимать без чтения всех модулей сразу.

## 9. Предлагаемый первый рабочий инкремент

Первый инкремент заканчивается после этапа 3: он уже должен обходить реальный проект и выдавать файлы, импорты и структуры, но ещё может не разрешать вызовы. После его проверки вызовы добавляются отдельным этапом, не усложняя базовый сбор AST-фактов.

Такой порядок позволит диагностировать ошибки по слоям: сначала файловая модель, затем определения, затем классификация и только потом наиболее неоднозначная часть — разрешение вызовов.
