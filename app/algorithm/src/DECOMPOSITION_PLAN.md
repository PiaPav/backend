# План декомпозиции сервиса анализа кода

## 1. Цель и границы

Текущий функционал `gpt_work_dir` необходимо разделить на два независимо существующих ядра:

1. **Parser**: принимает `Path` к исходному коду, строит полностью готовый семантический граф структур и связей, сохраняет его и возвращает `Path` результата.
2. **Metrics**: принимает `Path` к сохранённому графу, рассчитывает метрики, сохраняет результат и возвращает `Path` результата.

Ядра не импортируют и не вызывают друг друга. Их единственная общая точка — версионированные DTO файлов. Оркестрация, очереди, API, CLI и иной способ связывания ядер в этот план **не входят**.

Под «полностью готовым графом» понимается граф, в котором Parser уже выполнил семантическое разрешение импортов и вызовов. Metrics не должен повторно интерпретировать исходный код или разрешать строковые имена.

## 2. Текущее устройство

### 2.1. Parser

- `parser/logic/main.py` — текущие точки входа возвращают `dict`, а не файл.
- `analyzer.py` — координирует обнаружение файлов, AST, импорты, определения, классификацию классов, вызовы, сериализацию и валидацию.
- `project_index.py`, `imports.py`, `definitions.py`, `classifiers.py` — строят модель проекта.
- `scope.py`, `expressions.py`, `calls.py` — разрешают области видимости, выражения и вызовы.
- `models.py` — внутренние модели с AST и `Path`; они не подходят как межъядерный DTO.
- `serializer.py`, `validation.py` — формируют и проверяют фактически неформализованный JSON-контракт.
- `complexity.py` — сейчас рассчитывает производные метрики функций, смешивая обязанности Parser и Metrics.
- `source_index.py` — создаёт дополнительный артефакт исходников, не нужный Metrics.
- `parser/visualizer` — потребитель графа, а не часть ядра Parser.

### 2.2. Metrics

- `graph_metrics/calculator.py` — общий расчёт и агрегация.
- `architecture.py` — пакетные зависимости, циклы и архитектурные показатели.
- `call_graph.py` — SCC, центральности, пути и повторное эвристическое разрешение целей вызовов.
- `object_metrics.py` — объектные метрики.
- `quality.py` — агрегирует метрики функций, заранее рассчитанные Parser.
- `serialization.py` — сохраняет результат и уже возвращает `Path`.

Metrics сейчас принимает `Mapping`, не загружает граф по `Path` и не валидирует версию входного DTO.

### 2.3. Смешанный внешний сценарий

`analyze_project.py` связывает Parser, Metrics, source index и визуализацию. Он является оркестратором и не должен переноситься ни в одно из ядер. `graph_variants`, оптимизаторы и token-утилиты также не относятся к ядрам.

## 3. Целевая архитектура

### 3.1. Parser Core

Канонический файловый контракт:

```python
def parse_project(source_path: Path, output_path: Path) -> Path:
    ...
```

Обязанности:

1. проверить входной путь и обнаружить поддерживаемые исходники;
2. прочитать файлы и построить AST;
3. определить модули, пакеты, структуры, сигнатуры, аннотации и декларации;
4. построить области видимости и таблицы символов;
5. разрешить локальные и внешние импорты;
6. извлечь все callsite, включая повторные и вложенные;
7. разрешить цели вызовов либо явно зафиксировать `ambiguous`, `external`, `dynamic` или `unresolved`;
8. построить типизированные рёбра containment, import, inheritance, call/await и иные поддерживаемые связи;
9. присвоить стабильные идентификаторы узлам и callsite;
10. собрать нейтральные AST-факты, необходимые для последующих формул сложности;
11. проверить инварианты Graph DTO;
12. детерминированно и атомарно сохранить JSON и вернуть нормализованный `Path` только после успеха.

Parser не рассчитывает проектные рейтинги, центральности, агрегаты, пороги риска и иные производные метрики; не импортирует Metrics и не визуализирует результат.

### 3.2. Metrics Core

Канонический файловый контракт:

```python
def calculate_metrics(graph_path: Path, output_path: Path) -> Path:
    ...
```

Обязанности:

1. прочитать Graph DTO с устройства;
2. проверить JSON, версию схемы и структурные инварианты;
3. построить аналитические проекции уже готовых типизированных рёбер;
4. рассчитать размер, активность, сложность, качество, архитектурные, объектные и графовые метрики;
5. применить документированные пороги, нормализацию, сортировку и округление;
6. детерминированно и атомарно сохранить Metrics DTO;
7. вернуть нормализованный `Path` только после успешной записи.

Metrics не читает исходный код, не импортирует Parser, не принимает AST и не пытается заново разрешать импорты или вызовы.

### 3.3. Правило зависимости

```text
Parser Core  -> Graph DTO file
Metrics Core -> Graph DTO file -> Metrics DTO file
```

Общий код допустим только для декларативных DTO, схем, enum и чистой валидации формата. В общем пакете не должно быть бизнес-логики Parser или Metrics.

## 4. Общие DTO

### 4.1. Graph DTO

Рекомендуется версионированный JSON envelope:

```json
{
  "schema_version": 1,
  "parser_semantics_version": 1,
  "project": {"fingerprint": "..."},
  "nodes": [],
  "edges": [],
  "callsites": [],
  "diagnostics": []
}
```

Обязательные свойства:

- относительные POSIX-пути без обязательных абсолютных путей среды;
- `node.id`, `kind`, `qualified_name`, `parent_id`, location;
- `edge.source_id`, `target_id`, `kind`, locations;
- явное направление import: `dependent -> dependency`;
- явное направление inheritance: `child -> parent`;
- для callsite: owner, исходное выражение, location, syntactic depth, resolution, target/candidates;
- различение `exact`, `ambiguous`, `external`, `dynamic`, `unresolved`;
- сохранение повторных вызовов; если хранится вес, он равен числу соответствующих callsite;
- структурированные факты callable вместо финальных численных рейтингов.

Для фактов callable необходимы как минимум диапазон строк, управляющие конструкции с глубиной, statement count, `return`, `raise`, `await`, исключения, broad handlers, обращения `self.<attribute>` и признак async. Python AST в межъядерный DTO не передаётся.

Инварианты:

1. ID уникальны и стабильны при одинаковом входе.
2. Все внутренние ссылки ведут на существующие узлы.
3. Containment образует ациклический лес.
4. Каждый callable имеет ровно одного владельца.
5. Каждый callsite имеет ровно одного caller.
6. `exact` имеет одну внутреннюю цель, `ambiguous` — не менее двух кандидатов.
7. Повторные и вложенные callsite не теряются.
8. Неполнота анализа отражается в `diagnostics`.
9. Порядок сериализации детерминирован.

### 4.2. Metrics DTO

```json
{
  "schema_version": 1,
  "metrics_semantics_version": 1,
  "input": {
    "graph_schema_version": 1,
    "graph_fingerprint": "..."
  },
  "metrics": {}
}
```

Версия математической семантики должна меняться при изменении формул, порогов, нормализации или округления, даже если структура JSON не изменилась.

### 4.3. Совместимость

Миграция должна временно поддерживать чтение старого вложенного `body` и готовых `function.metrics` через адаптер. Канонический новый формат не должен наследовать неоднозначность старых строковых ссылок. Компактные `$columns/$rows` варианты не являются обменным DTO.

Source index остаётся отдельной опциональной возможностью Parser и не входит в обязательный `Path -> Path` контракт.

## 5. Распределение существующей логики

### Остаётся в Parser

- файловый discovery и AST;
- структуры и их классификация;
- scope и symbol resolution;
- разрешение импортов и вызовов;
- stable IDs и координаты;
- извлечение сырых фактов о control flow и callable;
- диагностика неполного статического анализа;
- валидация и сериализация Graph DTO.

Особенно важно перенести из `graph_metrics/call_graph.py` в Parser повторное разрешение целей, synthetic constructors и классификацию external/unresolved. Аналогично, эвристическое разрешение коротких имён родителей, типов полей и целей вызовов из `graph_metrics/object_metrics.py` должно стать обязанностью Parser. Graph DTO должен содержать готовые inheritance/type/coupling relations и классифицированные call targets с ID; DIT, NOC, CBO и RFC рассчитываются в Metrics только по этим узлам и рёбрам. Метрики должны видеть один уже определённый семантический граф.

### Переходит в Metrics

- cyclomatic и cognitive complexity, nesting и LOC по фактам Parser;
- размеры, средние и activity;
- degree, density, weak/strong components, SCC и циклы;
- bridges и articulation points с явным указанием неориентированной проекции;
- PageRank, betweenness, reachability и длины цепочек;
- coupling, instability, abstractness и distance;
- WMC, CBO, RFC, LCOM, DIT и NOC;
- пороги high complexity/deep nesting;
- risk, top-N, нормализация, округление и форматирование результата.

### Не входит ни в одно ядро

- `analyze_project.py` как способ оркестрации;
- visualizer;
- `graph_variants` и оптимизаторы;
- token counting;
- выбор транспорта или способ запуска двух ядер.

## 6. Поэтапный план работ

### Этап 1. Зафиксировать текущую семантику

1. Описать фактические поля старого graph JSON и потребности каждого модуля Metrics.
2. Создать golden Graph DTO и golden Metrics DTO для текущих fixtures.
3. Зафиксировать направления рёбер, правила `__init__.py`, вложенные вызовы и текущие численные результаты.
4. Устранить расхождение между документацией и реализацией `call_owner_count`: либо сохранить текущую формулу как legacy-версию, либо явно выпустить новую версию семантики.

### Этап 2. Ввести независимый файловый API Parser

1. Добавить `parse_project(source_path, output_path) -> Path`.
2. Переиспользовать текущий `ProjectAnalyzer`, не меняя сначала семантику графа.
3. Сделать сохранение атомарным и возвращающим resolved `Path`.
4. Сохранить текущие `starter*` как временный совместимый API.
5. Отделить source index и visualizer от публичного фасада ядра.

### Этап 3. Ввести независимый файловый API Metrics

1. Добавить loader и валидатор входного файла.
2. Добавить `calculate_metrics(graph_path, output_path) -> Path`.
3. Переиспользовать текущие calculator и serialization.
4. Централизовать чтение старого DTO, включая вычисление legacy file ID.
5. Проверить отсутствие импортов Parser и доступа к исходникам.

### Этап 4. Ввести версионированный Graph DTO

1. Добавить envelope и версии схемы/семантики.
2. Ввести canonical node IDs, file IDs и owner IDs.
3. Нормализовать import edges.
4. Перенести полное разрешение call targets в Parser.
5. Перенести в Parser разрешение inheritance, типов полей и coupling targets; сериализовать эти отношения по ID.
6. Добавить callsite locations, resolution status, candidates и multiplicity.
7. Перевести object metrics на вычисления только по готовым ID и типизированным рёбрам.
8. Ввести общий пакет DTO/схем без бизнес-логики.
9. Поддерживать legacy-поля на переходный период.

### Этап 5. Перенести формулы сложности в Metrics

1. Выделить из `complexity.py` извлечение AST-фактов отдельно от формул.
2. Сериализовать достаточные факты в Graph DTO.
3. Реализовать текущие формулы в Metrics без изменения результатов.
4. На переходе поддерживать старые готовые значения и новые facts.
5. После golden-эквивалентности убрать производные function metrics из нового Graph DTO.

### Этап 6. Централизовать аналитические проекции

1. Создать внутреннее read-only представление Graph DTO в Metrics.
2. Удалить дублирование `_file_id` и обхода вложенных calls.
3. Явно именовать directed import graph, call graph, package graph и undirected projections.
4. Запретить эвристическое изменение topology в Metrics.

### Этап 7. Закрепить независимость

1. Запускать тесты Parser без установки/импорта Metrics.
2. Запускать тесты Metrics только на статических Graph DTO fixtures.
3. Добавить статическую проверку запрещённых cross-imports.
4. Документировать каждый файловый контракт отдельно.
5. Удалить legacy adapters только отдельным версионированным изменением.

## 7. Проверки

### Контрактные и файловые

- оба API принимают `Path`, создают целевой файл и возвращают существующий resolved `Path`;
- ошибки не оставляют частичный файл, похожий на корректный результат;
- неизвестная версия и повреждённый JSON отклоняются явно;
- два запуска над одинаковым входом дают побайтово одинаковый JSON;
- перестановка nodes/edges во входном Graph DTO не меняет Metrics DTO;
- Parser и Metrics тестируются независимо.

### Golden cases

- пустой и однофайловый проекты;
- package и `__init__.py`;
- local/external/unresolved import и call;
- alias и одинаковые короткие имена;
- повторные, вложенные, рекурсивные и ambiguous calls;
- import cycle, isolated nodes, inheritance и abstract class;
- async/await, broad exception handler и control-flow edge cases.

### Математические инварианты

- отдельно `sum(in-degree) == E` и `sum(out-degree) == E`; их общая сумма равна `2E`;
- `average_fan_in == average_fan_out == E/N`;
- density, instability, abstractness, distance, resolution rates и LCOM находятся в допустимых диапазонах;
- SCC образуют разбиение, а condensation graph ацикличен;
- сумма PageRank приблизительно равна 1, значения неотрицательны;
- `local + external + unresolved (+ dynamic/ambiguous согласно контракту) == total callsites`;
- сумма весов локальных рёбер равна числу локально разрешённых callsite;
- risk находится в `[0, 100]` и документирован как относительная эвристика, а не вероятность.

Следует заморозить версиями: правила cyclomatic/cognitive complexity, PageRank (`damping=0.85`, tolerance и лимит итераций), нормировку betweenness, пороги сложности, top-N/tie-break, округление, веса risk `0.35/0.25/0.20/0.20`, обработку нулевых знаменателей и определение package.

## 8. Основные риски и решения

1. **Изменение чисел при переносе complexity.** Сначала golden-фиксация и двойной расчёт, затем переключение.
2. **Потеря вызовов при нормализации.** Хранить каждый callsite и выводить вес из multiplicity.
3. **Разные графы в разных метриках.** Использовать единое DTO и явно названные проекции.
4. **Ложная точность статического анализа.** Хранить resolution и diagnostics; dynamic не считать exact.
5. **Утечка типов между ветвями scope.** До реализации корректного merge маркировать такие цели probable/ambiguous.
6. **Ломающая смена DTO.** Версии, legacy adapter и период параллельных golden-проверок.
7. **Скрытая связность через общую библиотеку.** Общий пакет ограничить DTO, enum, schema и чистой валидацией.

## 9. Критерии завершения декомпозиции

- Parser независимо выполняет `source Path -> versioned graph file -> Path`.
- Graph DTO содержит готовые структуры, типизированные связи и результаты разрешения целей.
- Metrics независимо выполняет `graph Path -> versioned metrics file -> Path`.
- Metrics не читает исходники и не выполняет семантическое разрешение.
- Между ядрами нет runtime-импортов и вызовов.
- Общими являются только документированные DTO и их декларативная валидация.
- Текущая численная семантика сохранена либо её изменение оформлено новой версией.
- Golden, contract, property и regression tests проходят раздельно для обоих ядер.
- В составе декомпозиции не появляется способ связывания или запуска ядер друг за другом.
